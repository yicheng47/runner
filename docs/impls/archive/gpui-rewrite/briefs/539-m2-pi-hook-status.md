**Injection, per invocation, nothing persisted (decision 4).** `session/pi_status.rs` embeds the extension source and installs it as `<app data>/pi-hooks/runner-status.ts` at startup, regenerated beside `copilot_status::install_plugin` in `start_runtime_watchers` (atomic write, gated on `hooks_supported(Pi)`), with `extension_dir`, `extension_path`, `install_extension` and `extension_available` in the Copilot plugin's shape. `router/runtime.rs` gains `pi_status_args(runtime, app_data_dir)` returning `-e <path>` when hooks are supported and the file exists, spliced by `trailing_runtime_args` for every pi spawn, resume and fork included, ahead of `--append-system-prompt` and the `--` goal. `hooks_supported` returns true for `Pi` on both platforms in the same change. `apply_runtime_args` sets four env vars on every pi spawn: `RUNNER_PI_STATUS_PATH` (`hook_path(hook_feed::status_path(app data, session id))`, forward slashes on Windows), `RUNNER_PI_STATUS_GENERATION` (a fresh UUID), `RUNNER_PI_SESSION_KEY` (the key the plan passes with `--session-id`) and `RUNNER_PI_REKEY_PATH` (`hook_path(claude_rekey::drop_path(app data, runner session id))`); it also removes a stale drop file before the spawn, as it does for Claude Code. `pty_runtime.rs` gains `HookStatusWatcher::Pi(PiStatusWatcher)`, started from the path and generation env vars like Copilot's.

**The extension.** A `.ts` file written without type annotations (so a Node test can run a copy as `.mjs`), an async default-export factory. At load it dynamically imports `VERSION` from `@earendil-works/pi-coding-agent` and registers nothing when the version is below 0.84.4 (an import failure counts as current); it registers nothing when `RUNNER_PI_STATUS_PATH` or `RUNNER_PI_STATUS_GENERATION` is unset; every handler returns early unless `ctx.mode === "tui"`. It reports with one `fs.appendFileSync` per event, one complete JSON line carrying `generation`, `hook_event_name` (pi's event type verbatim) and the fields the mapping needs inline, no payload file (`HookFeed::read_report` already accepts this): `session_start` (`reason`, `session_id` from `ctx.sessionManager.getSessionId()`), `agent_start`, `tool_execution_start` / `tool_execution_end` (`toolCallId`, `toolName`), `session_before_compact` (`reason`), `session_compact`, `session_compact_failed`, `message_end` for assistant messages only (`stopReason`, `errorMessage` truncated to 512 characters), `agent_settled`, `ui_prompt_start` / `ui_prompt_end` (`kind`, `title`), `session_shutdown` (`reason`). Rekey (decision 10): on every `session_start` whose `getSessionId()` differs from `RUNNER_PI_SESSION_KEY` and from the last id it reported, and `RUNNER_PI_REKEY_PATH` is set, it writes `{"session_id":"<id>"}` to a temp file in the drop directory and renames it over the drop path. Every write is wrapped so it can never throw into pi, and the extension prints nothing. The extension file doubles as the reporter path handed to `HookFeed::start_external`, so removing it is bridge loss.

**`PiStatusWatcher` mapping (decision 5).** `session_start` owns the generation except for `reason: reload`; `new`, `resume` and `fork` are turn boundaries that leave the session Idle with no outcome. Working from `agent_start`; `WorkDetail::UsingTools` while any `toolCallId` is between `tool_execution_start` and `tool_execution_end`; `WorkDetail::CompactingContext` from `session_before_compact` until `session_compact` or `session_compact_failed`. Idle only from `agent_settled`, never `agent_end`; the outcome is the last assistant `message_end` before settling: `stopReason: error` → `Failed`, `aborted` → `Interrupted`, anything else → `Completed`. `ui_prompt_start` raises one interaction: `confirm` → `WaitReason::Approval`, `select`, `input` and `editor` → `WaitReason::Answer`, `custom` → `WaitReason::Unknown`; `ui_prompt_end` clears it and `session_shutdown` clears every wait. `interrupt_signal` returns `None`: interruption arrives on the feed as `aborted`. If a live capture shows Esc during a turn does not reach the feed, wire Runner's input signal as Copilot does and say so in the handoff. Only an unresolved wait adds a crew delivery hold, through the existing normalized path.
