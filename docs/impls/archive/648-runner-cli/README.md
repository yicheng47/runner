# General `runner` CLI — program record

Archived after 0.11.0 was tagged on 2026-09-20 (`e9d59aa`, [v0.11.0](https://github.com/yicheng47/runner/releases/tag/v0.11.0)). The `runner` command is the way agents, scripts and people drive Runner; the app installs it on PATH and a `runner` skill into every detected agent's skills root; the MCP integration is gone.

Implementation record for [feature 648](../../../features/archive/648-runner-cli.md) ([#648](https://github.com/yicheng47/runner/issues/648)). The spec says *what*; this directory says *how, in what order, and what has landed*. Same shape as the [role-rename](../604-role-rename/README.md) record: this file is the condensed state and the decisions that bind, [plan.md](plan.md) is the mission table with what reading the code changed and the decisions taken along the way, [impl_log.md](impl_log.md) is the dated log, and the five briefs stay in [`../../briefs/`](../../briefs/).

Mission 1 ([PR #650](https://github.com/yicheng47/runner/pull/650), 2026-09-18) put every socket tool behind a `runner <noun> <verb>` command with references, `--json`, `-q`, tables and exit codes, and gave the socket a caller handle. Mission 2 ([PR #652](https://github.com/yicheng47/runner/pull/652), 2026-09-18) added `mission feed --follow`, `runner help agents`, the embedded skill on all five runtimes with TRAE's skills root, and the session commands. Mission 4 ([PR #654](https://github.com/yicheng47/runner/pull/654), 2026-09-19) put the command on PATH by default with an explicit Install for the rest and one switch for the skill, drawn first in `design/specs/648-runner-cli.pen`. Mission 3 ([PR #664](https://github.com/yicheng47/runner/pull/664) with the Windows test fix [#665](https://github.com/yicheng47/runner/pull/665), 2026-09-20) removed the MCP integration: the `runner-mcp` bridge, Runner registering itself, the pinned Settings → MCP row, with a once-only upgrade step that unregisters only the entries this installation wrote. Mission 5 ([PR #667](https://github.com/yicheng47/runner/pull/667), 2026-09-20) rewrote both READMEs around the CLI and the skill and refreshed the roadmap; the mission-watch skill in the memory repo switched to `mission feed --follow --json` the same day. #658 ([PR #660](https://github.com/yicheng47/runner/pull/660)) moved the crate to `crates/runner-cli` between missions 4 and 3.

The four-runtime gate passed: pi on nightly `5b6030a`, Claude Code, Codex and TRAE on `a61af39`, the nightly that also proved the production removal on an existing install (the entries pointing at the production bridge removed once, the stale bridge deleted, running sessions keeping their bridge process) and the default link into `~/.local/bin`. ## Decisions that bind

The spec's decisions 1–8 and its principles. The ones a crew is most likely to get wrong:

- **Inside a mission nothing changes.** `msg post`, `msg read`, `signal` and `ask` append to the event log directly, with no socket, no tokio runtime and no dependency on the app accepting connections. Only the control commands and the outside path use `mcp.sock`.
- **Identity is a handle or the person, never a location (decision 7).** Inside a mission the handle is `RUNNER_HANDLE`. Outside, `--as <handle>` becomes the tool's `from`, validated against the mission's roster by the tool, and no handle means `human`. `mission answer` is the person's verb and takes no `--as`. With a `from` handle the signal tool refuses the person's and the app's own types (`human_said`, `human_response`, `human_question`, `mission_goal`); without one it keeps today's whitelist.
- **A clean rename, no aliases.** `mission_post_human_message` and `mission_post_human_signal` become `mission_post` and `mission_signal`, as the `role_*` cutover did (#604). With decision 8 the CLI is the socket's only client.
- **The order inside 0.11.0 is fixed (decision 8).** Command tree, then the skill on all five runtimes and Jason's smoke of an agent driving a mission with no MCP entry, then the removal. `runner-mcp` keeps working until mission 3, because it is how missions 1 and 2 are launched and watched.
- **One binary.** The control commands live in the same `runner` the mission sessions already have on PATH. No second binary, no scoping by packaging.
- **No new dependencies without a reason in the handoff.** `clap`, `tokio` and `rmcp` are already in `crates/runner-cli/Cargo.toml`; tables are hand-rolled.

## Open

- The Windows half never ran on a fresh install: the sidecar directory on the user PATH, a new PowerShell finding `runner`, Uninstall, the skill's quoted path from PowerShell and Git Bash, and the upgrade path's `[InstallDelete]` and bridge unregistration. [#668](https://github.com/yicheng47/runner/issues/668), with the pi checks and the README's Settings → MCP screenshot, which still shows the pinned row.
- The upgrade step, the per-client status and write functions, the bridge name constant and the stale-file cleanup exist only to clean up after 0.10 installs; one small removal once every user is past 0.11.
- A deferred client is retried on a runtime refresh within the session as well as at launch; a permanently unparseable config keeps the step pending and logs one line per refresh, the intended cost of the Deferred policy.
- Left unfiled from the missions: an Enter written to an Idle baseline session flips the manager to Busy through `input-submit` without arming the PTY idle detector, so a silent agent leaves the row Working; an armed Codex session whose turn ends in an error never returns to Idle; `mission start` prints the crew id where `mission show` prints the name; a `mission_get` failure after a successful resume surfaces as an error.
- The MCP framing on the socket is the wrong shape for what [#562](https://github.com/yicheng47/runner/issues/562) and [#645](https://github.com/yicheng47/runner/issues/645) want (push, identity on the connection, a protocol that forwards over ssh); the registry stays as the API and the framing goes when the first of them needs it.
- #562 builds its coordinator verbs (`spawn`, `ps`, `wait`, `stop`, `done`) and the seats an outside agent takes on this CLI; exit code 4 is reserved for its `wait`.
