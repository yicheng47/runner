# 437 — Windows nightly: implementation plan

Tracking issue: [#437](https://github.com/yicheng47/runner/issues/437). Feature, P2. Spec: [`docs/features/archive/437-windows-nightly.md`](../../../features/archive/437-windows-nightly.md) — the spec wins on any detail this plan leaves out, except the dated amendments under Decisions. Baseline `main` at `08e2bf7` (v0.7.5, 2026-09-05). Phase 0–3 pointers are to that baseline; re-grep before editing. Phase 4 started on 2026-09-06 with unsigned installers for testing; signing follows separately.

## What ships

A public `nightly-win` pre-release built by `nightly.yml` from `nightly-windows`. Phases 0–3 delivered a portable x64 ZIP containing `Runner.exe`, `runner-agent-cli.exe`, and `runner-mcp.exe`. Phase 4 replaces it with a per-user EXE installer as the only Windows download; signing follows in Stage 4b. Jason retired portable ZIP distribution on 2026-09-06. Runner detects newer builds; the user clicks the update indicator, downloads and runs the installer, and upgrades the existing installation while keeping settings and missions. Automatic download and installation remain later work. Direct chats and crew missions use ConPTY, Job Objects, both CLI shims, and named-pipe MCP. macOS behavior and its Sparkle updater remain unchanged.

## Where it touches

Organized by phase so each mission takes one slice. Line numbers are on the baseline.

### Phase 0 — compile gate

- `crates/runner-backend/Cargo.toml:47-50` — `portable-pty` is under `[target.'cfg(unix)'.dependencies]` beside `libc`; it must build on Windows (its ConPTY backend already does). Move it to plain `[dependencies]`; keep `libc` unix-only; add `[target.'cfg(windows)'.dependencies] windows-sys` with `Win32_Foundation`, `Win32_System_JobObjects`, `Win32_System_Threading`. The lockfile already carries `windows-sys` through gpui-ce, so nothing new resolves.
- `crates/runner-core/src/app_paths.rs` (new) — the one place that knows where things live. `home_dir()` wraps `std::env::home_dir()` (un-deprecated since 1.87; the toolchain is 1.97.1), which reads `HOME` on unix and the profile folder on Windows. `app_data_dir(debug)` returns `~/Library/Application Support/<id>[-dev]` on macOS, `$XDG_DATA_HOME`-or-`~/.local/share/<id>` on Linux, `%APPDATA%\<id>[-dev]` on Windows. `log_dir(debug)` returns `~/Library/Logs/<id>` on macOS and `<app_data>/logs` elsewhere. `mcp_endpoint(app_data_dir, debug)` returns the socket path `<app_data>/mcp.sock` on unix and the pipe name `\\.\pipe\com.wycstudios.runner[-dev]` on Windows. `runner-core` has no tokio dependency, so this module stays pure path logic and both binaries can use it.
- `crates/runner-app/src/bootstrap.rs:66-85` — `native_paths` / `paths_for_home` hardcode `Library/Application Support` and read `HOME` directly. Replace with `app_paths`; keep `paths_for_home(home, debug)` as the unit-tested seam and add Windows and Linux cases to the tests at `:281-290`.
- `cli/src/mcp.rs:16-33` — `app_data_segment` and `socket_path` duplicate the same derivation with `cfg(target_os)` branches and no Windows arm (one of the two compile errors in the CLI). Replace with `app_paths::mcp_endpoint`.
- The remaining `HOME` reads — `ops/mcp.rs`, `router/runtime.rs`, `runtime_status.rs` (2), `session/codex_capture.rs` (2), `session/manager/mod.rs`, `session/manager/spawn.rs` (3), `session/pty_runtime.rs`, `runner-terminal/src/terminal.rs`, `surfaces/mission_workspace.rs` (2), `surfaces/panes.rs` (2), `surfaces/start_chat.rs` (2) — become `app_paths::home_dir()`. Mechanical; one commit.
- `crates/runner-backend/src/ipc.rs` (new) — server side of the transport. `IpcListener::bind(&IpcEndpoint)` and `IpcListener::accept() -> IpcStream`, where `IpcStream` implements `AsyncRead + AsyncWrite` and has `into_split()`. Unix: `tokio::net::UnixListener` exactly as `mcp/mod.rs:111-127` does today, including the unlink-before-bind. Windows: `tokio::net::windows::named_pipe::ServerOptions`; the accept loop creates the next instance before serving the current one (the documented tokio pattern), `first_pipe_instance(true)` on the first so a second app instance fails loudly instead of sharing the pipe.
- `crates/runner-backend/src/mcp/mod.rs:4-8,40-127` and `mcp/server.rs:46-47` — `McpHandle::start` binds through `IpcListener`; `serve_connection` takes `IpcStream`. `socket_path` on the handle (`:105`) becomes `endpoint() -> IpcEndpoint`; its `Display` is what the settings page shows.
- `cli/src/ipc.rs` (new) and `cli/src/mcp.rs:124-150` — client side. Unix: `UnixStream::connect` as today. Windows: `ClientOptions::new().open(name)`, retrying `ERROR_PIPE_BUSY` (231) every 20 ms inside the existing `CONNECT_TIMEOUT`. The "Runner.app is not running" messages at `:136,143` stay, with the endpoint's `Display` in place of the path.
- `crates/runner-backend/src/ops/mcp.rs:2,305` — `OpenOptionsExt::mode(0o600)` behind `cfg(unix)`; the permission assertions in its tests at `:523-569` likewise.
- `crates/runner-app/src/surfaces/settings/mcp.rs:177,249` — `parent_path(&status.socket_path)` shows the binding directory; on Windows show the pipe name itself. Rename the status field to `endpoint`.
- `crates/runner-backend/src/session/mod.rs:16-17` — drop the `#[cfg(unix)]` on `pty_runtime`. Everything in it that touches `libc` moves to the `process` module below, so the file itself compiles on both.
- `crates/runner-backend/src/session/process/` (new: `mod.rs`, `unix.rs`, `windows.rs`) — the lifecycle seam. `mod.rs` declares one signature set and `#[cfg]`-selects the implementation; the unix file is `pty_runtime.rs:363-371` (`distinct_foreground_process`), `:515-547` (`signal_process_group`, `signal_process`), `:1051-1083` (`live_descendants`), `:1085-1132` (`reap_descendants`, `process_exists`), `:1134-1231` (`process_command_line` and its parser), and `:1265-1277` (`wait_for_process_exit_until`) moved verbatim plus `spawn.rs:71-76,273-278` (`process_group(0)`, `terminate_headless_fork`). The Windows file in Phase 0 is stubs that compile and return `Unsupported` / empty; Phase 2 fills them in. The signature set:

  - `ProcessTree::has_other_processes(&self) -> io::Result<bool>` — replaces `distinct_foreground_process` for `has_foreground_process` (`:344-361`). Unix: `tcgetpgrp` as today. Windows: `QueryInformationJobObject(JobObjectBasicAccountingInformation).ActiveProcesses > 1`.

- `crates/runner-backend/src/ops/session.rs:871-873,889` — `resolve_shell_command` falls back to `/bin/zsh`. Windows order: `pwsh.exe` on `PATH`, then `powershell.exe`, then `%ComSpec%`. The `SHELL` read stays first so a Git Bash user who sets it gets it.

### Phase 2 — agents run

- `crates/runner-backend/src/session/process/windows.rs` — the real implementations of the Phase 0 stubs, per the signature set above. `process_exists` is `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + `GetExitCodeProcess == STILL_ACTIVE`. `process_command_line` is `QueryFullProcessImageNameW`, which yields the image path only; see the orphan-sweep note below for why that is enough.
- `crates/runner-backend/src/session/pty_runtime.rs:249-291` (`stop`), `:373-495` (`stop_and_reap_child`, `stop_child_owned_by_reader`) — the two-tier `SIGHUP` → `SIGKILL`-the-group escalation with `HUP_GRACE` (`:48-50`) becomes, on Windows, one tier: `ProcessTree::terminate` then poll `try_wait` for `KILL_GRACE`. The unix path is unchanged. `reap_descendants` after a successful stop is a no-op on Windows because the job already took the tree.
- `crates/runner-backend/src/session/pty_runtime.rs:948-1034` (`cleanup_orphan_processes_on_startup`) — on Windows the sweep only clears recorded pids from rows and never kills: `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` means the kernel terminated every session tree when the previous app process exited, crash included, because the job handles closed with it. The command-line identity check (`:1232-1263`) that guards against pid reuse therefore has nothing to guard on Windows; `process_command_line` stays available for logging only.
- `crates/runner-backend/src/session/manager/spawn.rs:57-60` and `pty_runtime.rs:164-167` — env-name validation already rejects names that `CommandBuilder::env` would refuse; no change. `spawn.rs:614,2041` prepend `<app_data>\bin` to `PATH`; correct as-is once `compose_path` joins with `;`.

Values are ULIDs and paths; the writer errors on `"` or `%` in a value rather than growing an escaper. `sh_escape` (`:163-166`) stays for the `sh` shim. The `#[cfg(unix)]` chmod blocks at `:88,158` stay; NTFS has no execute bit.

- `crates/runner-backend/src/session/codex_capture.rs` — `open_rollout_paths_for_pid` is `lsof` on macOS and `Unsupported` elsewhere; the marker-scan fallback already covers Windows. Leave it; confirm a codex direct chat still records a resume key through the fallback.

### Phase 4 — Windows installer and upgrades (remaining)

Started at Jason's request on 2026-09-06. This phase extends the port to the installation and update mechanism discussed after the crew smoke test passed. Rollout is staged: **4a** implements and validates unsigned installers; **4b** selects a signing provider, configures credentials, and signs the distribution. Signing does not block local installer testing. The first public installer shipped in nightly `20260906.0842`; Jason subsequently selected installer-only distribution.

- **Installer.** Use Inno Setup to produce `Runner-Setup-<version>.<stamp>-x64.exe`. Install for the current user under `%LOCALAPPDATA%\Programs\Runner` without requiring administrator privileges. Keep the app and both CLI sidecars together, add a Start Menu shortcut and an Installed Apps/uninstall entry, and use a stable installer identity and directory across upgrades. Keep installer scripts separate from macOS packaging.
- **Upgrade and data.** The update indicator opens the Windows release/download page; the user downloads the newer installer, closes Runner normally, and runs it over the existing installation. Replace all three executables together, including nightlies with the same crate version and a newer build stamp. Preserve the existing `%APPDATA%\com.wycstudios.runner` database, settings, missions, and logs. Uninstall removes application files and shortcuts while retaining user data by default. Prompt for a normal close if Runner is running; do not terminate an active mission merely to replace files.
- **Signing and CI.** Extend only the Windows path of `.github/workflows/nightly.yml`: build and sign the app/sidecars, package with Inno Setup, sign the installer and uninstaller, verify signatures, and publish the installer on `nightly-win`. The signing provider/certificate and CI credentials are still to be configured. Keep a reproducible build identity, publish only the installer, and remove the retired portable ZIP assets. Leave `release.yml`, macOS signing, and the macOS nightly's draft policy unchanged.
- **Update detection and UI.** Update `crates/runner-app/src/updater/windows.rs` to recognize completed installer assets and compare their build stamps. Update `surfaces/settings/updates_windows.rs` and Windows tooltip/download text to describe installer upgrades. Preserve `RUNNER_DEV_UPDATE_AVAILABLE` for debug previews, keep older/equal builds from appearing as upgrades, and handle the transition from ZIP-only releases. Automatic download, silent installation, and app-managed restart are not part of this phase.
- **Documentation.** Replace the primary ZIP/extract instructions with installer and upgrade instructions, remove portable ZIP download instructions, and record the tested installer version and results in `impl_log.md`.

Stage 4a implementation lives in `script/bundle-windows.ps1` and `script/windows/`: a SHA-256-pinned portable Inno Setup 6.7.3 compiler, the installer definition, isolated installer smoke tests, and release notes. The build command stamps the app and packages only the EXE installer. `ignoreversion` ensures same-version nightlies replace every binary; writable-file probes run before installation/uninstallation, and Restart Manager closing/restarting is disabled. The installer does not write to or remove Runner's AppData directory. The Windows checker accepts completed installer assets alongside legacy ZIPs. Windows CI tests the installer definition with temporary executables; nightly packaging repeats the test with the actual release payload before publication. No signing credentials are configured yet.

Direct EXE distribution through GitHub does not require a Microsoft Store developer account. Signed releases need a signing provider and publisher identity validation; verify country eligibility when selecting the provider. As checked on 2026-09-06, Azure Artifact Signing's public-trust regions do not include mainland China, so a China-based publisher needs another eligible provider. Microsoft Store registration is a separate distribution choice. References: [Windows code signing](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options), [Azure signing prerequisites](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart).

## Decisions

- **2026-09-06 installer phase.** Jason first requested recording the EXE installer and manual upgrade mechanism, then authorized implementation. Start with unsigned installers for testing; signing follows as Stage 4b. Phase 4 includes the per-user Inno Setup installer, eventual signed release artifacts, and update-indicator-to-installer flow with data preservation. This supersedes the original ZIP-only scope and installer/signing exclusions.

- **2026-09-06 Windows update indicator.** Jason requested the existing sidebar update button and debug environment preview on Windows. The Windows implementation now checks uploaded x64 ZIP timestamps on `nightly-win`, shows a download indicator for a newer packaged nightly, and opens the release page when clicked. Settings exposes automatic/manual checks and manual downloads. Automatic installation remains outside this migration's scope; macOS retains Sparkle. The earlier “no updater” boundary allows these notifications and manual-download controls.

- **2026-09-06 keymap update.** Jason requested Cmd → Ctrl for Windows, preserving existing Shift modifiers. This supersedes the keymap portion of the earlier spec amendments below, including their extra Shift/Alt and PageUp/PageDown substitutions. Ctrl+C copies a terminal selection and otherwise reaches the PTY; app shortcuts take precedence over matching terminal chords. Fullscreen remains F11, and macOS defaults are unchanged.

- **A long-lived `nightly-windows` branch, not `main`.** Decided by Jason 2026-09-05 after Phase 0 was reviewed: every Windows phase PR bases on and merges into `nightly-windows` (created from `main` at `7cf7dd1`, checked out in the `../runner-windows` worktree), `nightly.yml` builds the Windows zip from that branch, and the distinct `nightly-win` release tag targets it (a tag must not share the branch name). `main` stays the macOS product; `ci.yaml` triggers on both. Phase 0 landed there as [#482](https://github.com/yicheng47/runner/pull/482) (`9a213e5`). The separate `nightly-win` tag and the explicit nontransparent Windows title bar were approved as plan corrections on 2026-09-05.

- **Two spec amendments.** (1) Keymap: the spec's example puts app chords on bare `Ctrl` (Ctrl+N, Ctrl+W, Ctrl+K). In a terminal `Ctrl+W`, `Ctrl+K`, `Ctrl+D`, `Ctrl+H`, `Ctrl+S`, `Ctrl+C`, and `Ctrl+V` are all shell or readline keys, and Runner's focus is in a PTY most of the time. Windows Terminal itself binds `Ctrl+Shift+<letter>` for exactly this reason. So the rewrite is `cmd-<letter>` → `ctrl-shift-<letter>` and `cmd-<non-letter>` → `ctrl-<same>`, which keeps `Ctrl+,` for settings and `Ctrl+1…9` for tabs as the spec wanted. Phase 1 review amendment, approved by Jason 2026-09-05: brackets must also reach the terminal (Ctrl+[ sends ESC), so pane/mission cycling uses Ctrl+PageUp/PageDown and page history uses Ctrl+Shift+PageUp/PageDown. Shifted letter collisions add Alt; unsupported Hide/Hide Others are omitted, and MissionFeed Copy is Ctrl+C. (2) Startup orphan sweep: the spec asks for `QueryFullProcessImageNameW` so the sweep can verify identity before killing. With `KILL_ON_JOB_CLOSE` the sweep has nothing to kill, so on Windows it only clears rows; the image-name query stays for logs.
- **A cfg-split module, not a runtime trait.** The spec says "a platform trait with two implementations". A module with one signature set selected by `#[cfg]` is that trait resolved at compile time: no `dyn`, the unix half moves verbatim, and a missing Windows function is a compile error in the `Rust / Windows` job rather than a panic on the PC.
- **One-tier stop on Windows.** No grace window before `TerminateJobObject`; see Phase 2. Revisit only if an agent is shown to leave state behind that a `CTRL_CLOSE_EVENT` would have flushed.
- **Job assignment after spawn.** `portable-pty` does not expose `CREATE_SUSPENDED`, so the child runs for a few milliseconds before `AssignProcessToJobObject`. Anything it forks in that window escapes the job. Agent CLIs spend their first hundreds of milliseconds loading Node; accepted, and noted here so nobody chases a phantom later. If it bites, the fix is a `portable-pty` patch, not Runner-side polling.
- **Shared path logic lives in `runner-core`.** It is the one crate both the app and the CLI depend on and has no tokio, so it takes the pure pieces (`app_paths`) and the async halves stay in the crate that already has the runtime.
- **Test gates are `cfg(unix)`, not rewrites.** Fourteen files spawn POSIX commands to exercise unrelated logic; twins are written only where the Windows behavior is the thing under test (`pty_runtime.rs`).

## Rules of the road

- No macOS behavior change in any phase. A reviewer diffs with `--color-moved` and rejects a phase whose unix code changed in anything but location.
- Crews never run the app on either machine. Over `ssh pc` they read logs and process lists, nothing more; every "works on the PC" claim about the GUI is Jason's. A mission's handoff says what it verified (CI jobs) and what it hands to the PC checklist.
- Mission authorization is PR mode per phase: commit, push, open the PR, drive CI green including the Windows job. Merge is Jason's. `nightly.yml` dispatch is Jason's (it restarts his Mac app on the macOS path).
- Follow existing patterns: `Error::msg` in the backend, `anyhow::Context` in the app, `eprintln!` for boot-time reports, `log::warn!` in the backend. No new error types; `windows-sys` calls wrapped in small `io::Result` functions in `process/windows.rs` and `ipc.rs` only.
- Do not touch `release.yml`, macOS signing, or the macOS nightly's draft policy. Windows signing is part of Phase 4.

## Non-goals

A production Windows channel, automatic update download/installation, WSL, ARM64 Windows, Linux, and unrelated Windows UI changes remain outside scope. The installer, Windows signing, update notifications, and user-run upgrades are in scope for Phase 4. Also out: making the macOS nightly public, and any refactor of `pty_runtime.rs` beyond extracting the `process` module (file splits are #478 passes 2–4).
