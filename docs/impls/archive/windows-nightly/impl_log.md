## 2026-09-05 — Todo 1: ConPTY cursor jump

Jason's PC pass on the 1323 zip: a codex direct chat opens and echoes (expected — Phase 0's ConPTY spawn and PATHEXT lookup), but the cursor jumps during codex redraws. Not seen on macOS. Cause, read against alacritty_terminal 0.26 `event_loop.rs` and Zed's `crates/terminal`: ConPTY re-emits whole screens without synchronized-update markers; Runner read 8 KB per event and took the terminal lock per event, so the renderer could paint half a redraw with the cursor at ConPTY's intermediate position. Fix mirrors alacritty (drain under one lock) and Zed (4 ms wake batch): the forwarder in `manager/output.rs` merges immediately queued `Stream` chunks up to 1 MiB into one ingestion, `READ_BUF` is 64 KB, and `app_store.rs` batches wakeups for 4 ms before one `cx.notify()`. Portable code, no `cfg(windows)`. Mission `01M1S0W92N4FS25XEX9Y9CWTV7`, one review round with no must-fix; the reviewer's should-fix pinned the input-state tracker against a composer echo and clear arriving in one chunk. [#486](https://github.com/yicheng47/runner/pull/486), merge `36f98eb`. Jason checks on the next nightly: no intermediate cursor positions during a codex redraw, composer typing latency unchanged.

Coder's known limitations, kept verbatim below.

### Phase 2 known limitations

Job assignment happens after spawn, so descendants created before assignment can escape and a headless descendant holding inherited pipes can block reader joins; `portable-pty` does not expose suspended spawn. Windows Stop has one tier: terminate the job, then wait up to two seconds. Agents get no cleanup hook on Windows Stop. Windows job membership includes background helpers, unlike Unix foreground-process-group detection. The Windows command-line helper returns only the image path; startup cleanup clears recorded pids without process identity checks or kills.

## 2026-09-06 — Windows close ownership and remaining cursor drift

Jason reported `0x80040102`, `0x80070578`, and `window not found` at 05:20:16 UTC; the listener shut down immediately afterward. In gpui-ce 0.3.3, accepting native `WM_CLOSE` lets Windows destroy the HWND, then `WindowsWindow::drop` calls `RevokeDragDrop` and `DestroyWindow` on it again. A temporary hidden native window reproduced both HRESULTs. Closing via `Window::remove_window()` and vetoing the OS default handler removed both invalid-handle errors in the same probe. Runner now uses that close path in `platform_ui/windows.rs`; the macOS close callback still returns true. The temporary probe was removed. Both subsequent Runner runs at 05:34 UTC have no invalid-handle HRESULTs, but each still logs one `window not found` immediately before shutdown. GPUI defers its Windows activation callback, which can outlive the window; this is a suspected source, not a confirmed diagnosis of the remaining message.

Jason confirms the cursor batching significantly improves the drift but does not eliminate it. The new `target/cursor-followup` recordings contain zero misplaced busy cursor positions in the resumed chat and exactly one in the new chat when replayed at the 149 × 49 grid recorded in Runner's resize log. At 2106 ms the cursor leaves the composer row and ends above the busy indicator, immediately after a synchronized-update end; the following output event restores it at 2184 ms. These recordings are taken after batching, so the 78 ms gap does not measure the raw ConPTY delay.
