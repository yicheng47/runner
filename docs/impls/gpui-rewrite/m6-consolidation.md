## Why a milestone, not a backlog

M3–M4 are parity work: the gate is "same as `main`". Everything here is *beyond* `main` — fixes `main` also has, refactors the agentic build never volunteered, and one new capability. Left as a backlog it does not happen: the audit's own finding is that local patches accumulate and global refactors do not, unless someone schedules them. So M6 is a named stage with ordered missions and gates, like M4.

Two items that look like M6 are deliberately placed elsewhere:

- **Terminal selection and copy is M4.7**, not M6. xterm.js has selection and ⌘C natively, so its absence on the GPUI line is a parity gap and a daily-driver blocker, and it belongs under M4's exit gate.
- **Hook-based session status (#347, feature 52) is M6.2, the first post-GA mission (M6.1 landed first, 2026-08-22)** — not pulled forward onto `main`. `main` is feature-frozen (plan decision 11, 2026-08-20): Jason will not carry two versions; the rewrite finishes, then the switch happens, then the work beyond parity starts. Feature 52 was specced against `src-tauri` paths; the port mapping is `src-tauri/src/*` ↔ `crates/runner-backend/src/*`.

### M6.16 — Descendant sweep by env tag at session stop and startup — S/M, backend, before `v0.6.0` (Jason, 2026-08-22, after the M6.3 reviewer's stress loops ran the host at load 306 for three hours)

Today `session/pty_runtime.rs::stop_and_reap_child` sends SIGHUP to the agent through the PTY and escalates to `kill(-pid, SIGKILL)` — the agent's process group — only if the agent survives the grace period; claude-code and codex exit cleanly on SIGHUP, so the group kill rarely runs. It would not have helped anyway: Claude Code's Bash tool runs each command in its own process group (verified 2026-08-22 — a wrapper's `pgid` is its own pid, not Claude's), so anything a command backgrounds lives in a group Runner never sees and is reparented to launchd the moment the command finishes. The startup orphan sweep (`pty_runtime.rs` ~925) targets only the recorded agent pid with a command-line match, so grandchildren are invisible there too. Result: 180 `while :; do :; done` subshells from a reviewer's "8× oversubscription" test survived its session by three hours and starved every TUI on the machine (impl_log 2026-08-22).

Two layers, because they catch different things (Jason, 2026-08-22 evening: "use a signal and let the TUI do the job"). **Layer 1 — let the agent clean up its own tracked children.** claude-code 2.1.239 installs handlers for SIGHUP, SIGINT and SIGTERM, spawns tool commands detached in their own process groups (`setsid`), and on shutdown kills those groups (`kill(-pid)` sites in the bundle) — so the SIGHUP Runner already sends through the PTY lets a *running* command and tracked background tasks die with the agent. Verify the same for codex (`codex-code-mode-host` and shell children), give the grace period enough room for that cleanup to finish before the SIGKILL escalation, and record which signal each runtime cleans up on. **Layer 2 — the sweep below**, because no TUI can reach what it has already lost: today's 180 loops were backgrounded inside a command that *completed*; they were reparented to launchd minutes before the session ended, in a process group the agent no longer tracked. Only something that recognises them by inherited env can find them.

**Layer 2 is deferred (Jason, 2026-08-22 evening): "a very edge case — the agent should remember."** The design is recorded for when it is needed: every process a session spawns inherits Runner's injected env (`RUNNER_HANDLE`; mission slots also carry `MISSION_CWD` — a `RUNNER_SESSION_ID` tag would make it unambiguous); macOS exposes another process's env through `sysctl KERN_PROCARGS2` (same uid), so a stop-time and startup sweep could `proc_listallpids`, read each env, and SIGKILL anything tagged with a session that is no longer live — milliseconds per scan, never matching on command line alone. Not scheduled. What ships instead for that case is the **crew-prompt guard** (both crews): "kill every background process you spawn before ending your turn; never leave load generators running" — the agent owns its leftovers.

Scope of M6.16 as scheduled: layer 1 only — verify the graceful-signal cleanup per runtime, size the grace period to it, record it. Gate: stop a claude and a codex session mid-command (a running `cargo test`, a background `sleep 600 &` task) — both die with the agent; `make verify`.

### M6.20 — Sidebar drop indicator survives the release — S, app crate (`sidebar.rs`), before `v0.6.0` (Jason, 2026-08-23: "when I drag a tab and release, the indicator line seems not to disappear")

Not yet traced; pointers from a read of `surfaces/sidebar.rs`: the drag state is `drop_target: Option<DropTarget>` plus the painted `drop_marker` (~183), set from the rows' `on_drag_move::<SidebarNodeDrag>` handlers (~2394, ~2508, ~2553, ~2618) through `update_row_drop_target` / `update_project_container_drop_target` (~1459-1500), and cleared by the `take()` at ~1451 on the `on_drop` paths (~2429, ~2517, ~2571, ~2637). Likely cause: the clear runs only when the release lands on a row or container that owns an `on_drop` listener, so letting go anywhere else — empty sidebar space, the dragged row itself, the gap between sections, past the end of the list, or an Escape mid-drag — never reaches it and the marker stays painted until the next drag. GPUI raises no drag-end event on the drag source; the pattern (Zed's pane tab bar) is one clear path that runs on any release — the root's `on_mouse_up` in the capture phase and `on_mouse_up_out`, which the window always receives even when no drop target fires — alongside the existing `on_drop`. Scope: that clear path plus a sidebar layout test that leaves a marker set and asserts it is gone after a mouse-up with no target. Gate: drag a chat row and release over empty sidebar space, over its own row, between PINNED and PROJECTS, past the last row, and press Escape mid-drag — no line remains in any case; reorders and project drops still work.

### M6.7 — Terminal render and ingestion performance (added 2026-08-21 from a read-only audit of the hot paths) — M, app + backend, after M6.1 unless streaming lag is felt first

Ranked by expected effect on perceived smoothness; "verified" = read in code, "inferred" = reasoned, not measured. The GPL guardrail holds — Zed's techniques are described, never copied.

1. **Every PTY chunk repaints the whole window** (verified). The waker feeds an unbounded channel; the drain bumps `revisions.terminal_wake` and notifies `AppStore` (`app_store.rs:239-262`), `main.rs:723-724` turns that into a `NativeRoot` notify, and the root's render (`app_shell.rs:49-93`) rebuilds sidebar, workspace, overlays and every pane. The M4.4 gate (`route.terminal_visible()`) only stops non-terminal routes — output from any attached session, including background panes and other tabs, re-lays-out the whole tree. Fix: terminal view as its own entity, notified per session; the shell only when its layout depends on it.
2. **Full grid walk + shaping every frame under the fair `Term` lock** (verified). `element.rs:812-1090` holds `term.lock()` — contended with the feeder at `terminal.rs:368` — across the whole `display_iter` loop: palette resolution (`:877-878`), procedural-cell classification (`:922-935`), a `shape_line` for the cursor cell (`:1022`). Nothing is cached between frames. Fix: copy the renderable content into a snapshot under `lock_unfair`, rebuild layout only when the grid changed (Zed's `sync` / `last_content`).
3. **Per-cell `String` + `Vec<TextRun>` allocation; batching only for pure ASCII** (verified, `element.rs:997-1001`, `:1036-1069`, `:1092-1109`). One non-ASCII or restyled cell breaks the run, so CJK/emoji-heavy or per-cell-coloured TUIs degenerate to one allocation + shaping request per cell. Fix: batch on style equality alone and pass the cell width as the forced advance to `shape_line` — that removes the grid-skew reason the spike introduced the ASCII-only rule.
4. **Procedural glyphs re-tokenize their path strings every frame** (verified, `glyphs.rs:420`, `:483/:500` twice per stroke, `:423-425` tessellation per cell, `:129-143` a content mask per cell). Fix: precompute per-glyph geometry once per (cell size, scale factor). Absorbs Tier 2's "glyph path pre-parse".
5. **~23 linear scans of every chunk before it is encoded** (verified: `output.rs:889` → `update_terminal_mode_state` `:832-868`, six scanners over 20 needles, each a full `windows(n).rposition` pass, `mod.rs:87-101`; `terminal.rs:706-710` adds three). Inferred cost ~180 K byte comparisons per 8 KB chunk — the same order as alacritty's parse. Fix: one `memchr`-driven pass for `0x1b` with a small state machine.
6. **~11 copies + a JSON round-trip per chunk** (verified: `pty_runtime.rs:655` `to_vec` → `output.rs:890` base64 → ring clone `:912` → `events.rs:51-59` `serde_json::to_value` → broadcast, where six subscribers deep-clone the payload — `app_store.rs:266`, `main.rs:321`, `:357`, `windowing.rs:56`, `mission_workspace.rs:290`, `terminal.rs:721` — five of them discarding `session/output` — then `terminal.rs:350` decodes). Fix: raw `Arc<[u8]>` to attached sessions on a side channel; JSON stays for low-rate events. Absorbs Tier 2's "typed PTY event transport".
7. **Lag-storm feedback loop** (verified). On broadcast `Lagged` (`terminal.rs:739-746`) `resync_attached` (`:803-821`) re-feeds the entire 4,096-chunk ring synchronously under `feed_gate` — exactly when the app is already behind; the same ring retains up to tens of MB per session (`output.rs:912`).
8. **Hover/link scan under sustained output** (inferred): `refresh_hovered_link` runs every prepaint (`element.rs:785-794`); its signature includes `last_seq`, so with ⌘ held during streaming `link_at` rebuilds a whole wrapped line per frame (`terminal.rs:619-696`). Mouse-move itself does not storm — `:620-622` gates on `changed` (verified good). Fix: a grid-changed flag, as Zed's hover path uses.
9. Zed techniques absent here, in words: cached content snapshot refreshed on term events only; `lock_unfair` held only for the copy; style-only run batching with forced cell-width advance; viewport-intersection culling that skips all cell work for off-screen terminals; notifies scoped to the terminal view. One thing this line usefully lacks: no cursor-blink timer, so no idle repaint source (verified).

Scope: items 1–4 are the app-side mission; 5–7 the backend side (no behavior change, `main`'s router/manager suites must stay green). Measure first: frame time with a streaming codex slot in a four-pane tab, CPU per MB of PTY output. Gate: a streaming agent in a background pane no longer re-renders the foreground; per-frame allocations on a static grid drop to zero; `make verify`.

## Not doing, and why

- **fsync on the event log.** Page-cache durability is the right trade for a local tool; the cost is a hard power loss mid-append, and the log's tail repair already handles a torn line. Recorded as a decision in `arch.md` under M6.4.
- **Renderer damage tracking beyond M4.6b.** PTY bursts are already coalesced (`try_recv` drain), non-terminal routes are gated (`route.terminal_visible()`), and gpui's `LineLayoutCache` reuses shaped lines; M4.6b's per-entity notify removes the remaining whole-window re-render. A dirty-row set out of alacritty is L and nothing currently felt justifies it.
- **A quit path.** The audit listed its absence as a defect; it was refuted — `stop_running_sessions_on_quit` (`bootstrap.rs:194-209`) is wired from ⌘Q, window close, and post-`run()`, kills the process group (SIGHUP → SIGKILL), and joins the forwarder (`lifecycle.rs:96-97`). SIGHUP + the startup orphan sweep is the crash fallback. Only the `OutputStream` doc comment is wrong (M6.2).
- **M6.14 — settings as a YAML file under `~/.runner/` (spec 62), dropped 2026-08-22 (Jason).** Settings already are a plain JSON file — `ui-settings.json` in the app data dir, read at launch, written whole on change — and nobody edits it by hand, so a watcher, a new location and a format change bought nothing; the one gap, a hand edit needing a relaunch, is not worth a mission. The spec was deleted; this line and the impl_log are the record, and spec number 62 is the Monokai theme again, as on `main`.

### M6.6 — Terminal resize smoothness (was the `RESIZE_SETTLE_MS` experiment) — S/M, backend + app, **landed 2026-08-21 (`6f020d4`)** (promoted 2026-08-21, Jason: resize feels worse than Zed's embedded terminal; small and felt on every window drag)

Traced 2026-08-21. On every frame of a drag the resize owner's `prepaint` (`runner-app/src/terminal/element.rs:739-756`) pushes the new grid size into `TerminalSession::resize` (`runner-terminal/src/terminal.rs`), which on the UI thread, synchronously: (1) calls `ops::session::session_resize` → `SessionManager::resize` (`runner-backend/src/session/manager/output.rs:486-551`), which runs a SQLite `UPDATE` (`repo::session::update_last_size`) **per resize event** and then takes a second pooled connection for a `SELECT … FROM sessions LEFT JOIN runners` (`runtime_clears_on_resize`, `:926`) just to learn the runtime's resize policy; (2) for full-repaint runtimes (claude, codex) parks the PTY ioctl behind a settle thread for `RESIZE_SETTLE_MS = 175` (`manager/mod.rs:58`), so the TUI receives no SIGWINCH during the drag; (3) reflows the alacritty `Term` — 10,000 lines of scrollback — under its lock. Result: the grid shows old content reflowed into the new width for the whole drag, then snaps when the one settled SIGWINCH finally makes the TUI repaint, with two DB round-trips per frame in front of every reflow. Zed (reference only) calls `set_size` in `prepaint` every frame, resizes its `Term` and sends the PTY resize to its event-loop thread immediately — no persistence, no debounce — so the TUI redraws continuously and the content tracks the drag.

Why the 175 ms exists: a `main`-era contract (M3.3). For full-repaint runtimes `main` purges the output ring and injects `ESC[2J ESC[H` on every width change so later replays are width-coherent, and xterm's fit-addon produced storms, so an un-debounced storm meant purge/clear flicker. On the GPUI line the ring only matters for replay on re-attach (`TerminalBridge`, M4.6e); the live grid is alacritty's. The ioctl never needed to wait for the ring — only the purge does. `settle_pending_resize` already holds the pieces: purge + in-band clear + a rows-nudge round trip that forces a fresh full repaint.

Scope: (1) ioctl immediately on every resize for all runtimes; keep the settle solely for ring coherence — at settle, purge + the rows-nudge so the TUI's fresh repaint lands in a clean ring — no in-band clear, see the addendum below (the 2026-08-21 width-chain invariants must hold: forks read the persisted size; it is written once per storm, not per frame). (2) Take both DB calls off the per-frame path: cache `clears_on_resize` in `SessionState` at spawn/resume; persist `last_size` at settle or from a background thread. (3) Measure before and after: owner `prepaint` time during a width drag over a codex slot and a shell chat, ioctls per drag. Gate: a drag over a live codex slot tracks like Zed's terminal with no end-of-drag snap; `make verify`; the M3.3 coalescing tests rewritten to the new contract, not deleted.

Addendum 2026-08-21 evening (Jason: Zed's embedded terminal leaves Claude's history alone on resize, Runner's does not — anthropics/claude-code#58906 is the same symptom from Claude's side). The history duplication is ours, not the TUI's: the settle's in-band `ESC[2J ESC[H` is broadcast to every attached live grid (`settle_pending_resize`, `output.rs:649-664` → `feed_encoded_locked`), and alacritty 0.26 implements `ESC[2J` on the primary screen as `Grid::clear_viewport` — it scrolls the whole viewport into scrollback (`term/mod.rs:1788-1801`, `grid/mod.rs:309-333`). Apple's recommended form and what most native Mac apps ship; Tauri/Electron default to per-arch DMGs, which is why 0.5.x had two. Pulse is arm64-only (`pulse/script/bundle-mac:6`, `docs/macos-release.md`) and not a template. Cost: ~2× executable size inside the DMG (tens of MB) and ~2× the cargo step in CI (~10 → ~18 min warm). Feasibility: GPUI supports x86_64 — Zed ships Intel builds from the same code and gpui-ce is that code; nothing in the workspace is `target_arch`-gated (only `target_os = "macos"` / `unix`); every dependency that matters (gpui-ce, alacritty_terminal, portable-pty, objc2, bundled rusqlite) builds for x86_64; Sparkle.framework 2.9.5 is already universal; the Metal toolchain output is arch-independent; `MACOSX_DEPLOYMENT_TARGET` 12.0 covers Intel. **The updater is unaffected**: Sparkle compares `CFBundleVersion` and verifies the EdDSA and Developer ID signatures, never architecture — a universal DMG with a higher stamp is offered to the current arm64 nightly like any other.

Scope: `rust-toolchain.toml` gains `targets = ["aarch64-apple-darwin", "x86_64-apple-darwin"]` so local and CI get both; `bundle-mac` builds both triples, `lipo -create`s the three binaries (`runner-app`, `runner-agent-cli`, `runner-mcp`), asserts both slices, names `-universal.dmg` / `.zip`; `nightly.yml` adds the x86_64 target and widens the prune regex to `-(arm64|universal)\.dmg` so the older arm64 items still count toward the ten; the native `release.yml` (plan §Release channels) is written universal from the start with both platform keys in `latest.json`; README status/Download lines return to "Apple Silicon + Intel"; plan §Release channels names updated.

Testing without an Intel Mac: a local `./script/bundle-mac --channel nightly --dev` proves the cross-build and the `lipo`; Rosetta 2 runs the x86_64 slice on Apple Silicon — `arch -x86_64 "Runner Nightly.app/Contents/MacOS/runner-app"`, or Get Info → "Open using Rosetta" on the installed bundle (quit the running app first: one instance at a time) — which exercises PTY, grid, IME and Sparkle on the Intel code path. It does not exercise Intel/AMD GPU drivers, the one residual risk (Zed has had iGPU quirks on older Intel Macs). Hosted Intel runners are the paid `-large` tier; not worth it. Ship as "built and Rosetta-tested, reports welcome" — the README's Qoder/TRAE framing.

Gate: a nightly whose DMG's three binaries report `x86_64 arm64` under `lipo -archs`; the current arm64 install updates to it through Sparkle; the same bundle launched under Rosetta drives a claude chat; `make verify`.
