# 437 — Windows nightly: implementation plan

Tracking issue: [#437](https://github.com/yicheng47/runner/issues/437). Feature, P2. Spec: [`docs/features/437-windows-nightly.md`](../features/437-windows-nightly.md) — the spec wins on any detail this plan leaves out, except the two amendments called out under Decisions. Baseline `main` at `08e2bf7` (v0.7.5, 2026-09-05). Pointers below are to that baseline; re-grep before editing.

## What ships

A `nightly-windows` pre-release zip on the public releases page, built by `nightly.yml` from `main`, that a Windows user can download without a GitHub account and run: `Runner.exe` with `runner-agent-cli.exe` and `runner-mcp.exe` beside it, x64 only, unsigned, standard OS title bar, no installer, no updater. Direct chats and crew missions work natively on ConPTY with Job Objects for the process tree, the `runner` CLI reaches agents through both a `sh` and a `.cmd` shim, and the MCP proxy talks to the app over a named pipe. The macOS build, tests, and the `Rust / macOS` required check stay green after every phase; a non-required `Rust / Windows` check appears in Phase 0 and is promoted in Phase 3.

- `crates/runner-backend/Cargo.toml:47-50` — `portable-pty` is under `[target.'cfg(unix)'.dependencies]` beside `libc`; it must build on Windows (its ConPTY backend already does). ## The PC loop

`ssh pc` from the Mac lands in a PowerShell 5.1 session on Jason's Windows PC (`JASONPC`, user `ROG`, Windows 11; separate commands with `;`, there is no `&&`). The PC is a **run box, not a build box**: it gets what a friend would have, and nothing else. Decided 2026-09-05 when the first inventory started reaching for a full toolchain.

- Builds and tests come from CI. `Rust / Windows` on `windows-latest` is the compile and test gate; `nightly.yml` with `platform=windows` produces the zip. A mission never needs the PC to prove its code compiles.
- The PC runs the zip. Over ssh a mission may download a release asset, unzip it, inspect files, read `%APPDATA%\com.wycstudios.runner\logs`, and list processes (`Get-Process`, `tasklist`) to check for orphans after Jason's smoke test. It may not launch `Runner.exe`: a GUI started from an SSH session runs in a hidden session and proves nothing, and the crews-never-run-the-app rule holds on both machines.
- Nothing is installed on the PC unprompted. The baseline list is what the nightly's own release notes will ask a user for: Git for Windows (Claude Code's Bash tool runs through Git Bash, which is also what makes the `sh` shim resolve), Node.js LTS, `@anthropic-ai/claude-code`, `@openai/codex`. PowerShell 7 is not required; the shell pane falls back to `powershell.exe`. Rust and MSVC Build Tools stay off the PC unless the Phase 2 CI round trip becomes the bottleneck, and that is Jason's call.
- As of 2026-09-05 the PC is a clean slate: `winget` only, no git, Node, or agent CLIs, no `%USERPROFILE%\repos`.

## Plan

0. **Compile gate** — one mission, PR mode. Order inside the PR: `app_paths` + `HOME` sweep; `ipc` server and client with the socket path threaded through; `process` module extraction on unix with the Windows stubs; `portable-pty` dependency move and `pty_runtime` un-gated; `compose_path` / `find_executable` on `split_paths`; test gates; the CI job; `vision.md`. Done when `Rust / Windows` runs check and clippy green and `Rust / macOS` is unchanged. About one session.
1. **It opens** — one mission for the workflow and the app-shell changes (title bar, keymap rewrite, `NoShell` wording), then Jason dispatches `nightly.yml` with `platform=windows`, downloads the zip on the PC, and runs the Phase 1 checklist. Fixes land as small PRs. One to two sessions plus PC time. After this phase the friend already has a link.
2. **Agents run** — one mission for the Windows `process` module, the one-tier stop, the sweep change, both shims, and the test twins; then the Phase 2 acceptance on the PC, which is where the time goes. Expect two or three fix rounds. Three to five sessions.
3. **Polish** — one mission for the reveal/open commands, icon, manifest, notes; PC passes for resize and IME; promote the check. One session.

Each phase is its own PR off `main`; nothing in the branch may change macOS behavior, and the diff for a `#[cfg(unix)]` move must be a move (`git diff --color-moved` shows it as such).

## Decisions

- **Two spec amendments.** (1) Keymap: the spec's example puts app chords on bare `Ctrl` (Ctrl+N, Ctrl+W, Ctrl+K). In a terminal `Ctrl+W`, `Ctrl+K`, `Ctrl+D`, `Ctrl+H`, `Ctrl+S`, `Ctrl+C`, and `Ctrl+V` are all shell or readline keys, and Runner's focus is in a PTY most of the time. Windows Terminal itself binds `Ctrl+Shift+<letter>` for exactly this reason. So the rewrite is `cmd-<letter>` → `ctrl-shift-<letter>` and `cmd-<non-letter>` → `ctrl-<same>`, which keeps `Ctrl+,` for settings and `Ctrl+1…9` for tabs as the spec wanted. (2) Startup orphan sweep: the spec asks for `QueryFullProcessImageNameW` so the sweep can verify identity before killing. With `KILL_ON_JOB_CLOSE` the sweep has nothing to kill, so on Windows it only clears rows; the image-name query stays for logs.
- **A cfg-split module, not a runtime trait.** The spec says "a platform trait with two implementations". A module with one signature set selected by `#[cfg]` is that trait resolved at compile time: no `dyn`, the unix half moves verbatim, and a missing Windows function is a compile error in the `Rust / Windows` job rather than a panic on the PC.
- **One-tier stop on Windows.** No grace window before `TerminateJobObject`; see Phase 2. Revisit only if an agent is shown to leave state behind that a `CTRL_CLOSE_EVENT` would have flushed.
- **Job assignment after spawn.** `portable-pty` does not expose `CREATE_SUSPENDED`, so the child runs for a few milliseconds before `AssignProcessToJobObject`. Anything it forks in that window escapes the job. Agent CLIs spend their first hundreds of milliseconds loading Node; accepted, and noted here so nobody chases a phantom later. If it bites, the fix is a `portable-pty` patch, not Runner-side polling.
- **Shared path logic lives in `runner-core`.** It is the one crate both the app and the CLI depend on and has no tokio, so it takes the pure pieces (`app_paths`) and the async halves stay in the crate that already has the runtime.
- **Test gates are `cfg(unix)`, not rewrites.** Fourteen files spawn POSIX commands to exercise unrelated logic; twins are written only where the Windows behavior is the thing under test (`pty_runtime.rs`).

## Rules of the road

- No macOS behavior change in any phase. A reviewer diffs with `--color-moved` and rejects a phase whose unix code changed in anything but location.
- Crews never run the app on either machine. Over `ssh pc` they read logs and process lists, nothing more; every "works on the PC" claim about the GUI is Jason's. A mission's handoff says what it verified (CI jobs) and what it hands to the PC checklist.
- Mission authorization is PR mode per phase: commit, push, open the PR, drive CI green including the Windows job. Merge is Jason's. `nightly.yml` dispatch is Jason's (it restarts his Mac app on the macOS path).
- Follow existing patterns: `Error::msg` in the backend, `anyhow::Context` in the app, `eprintln!` for boot-time reports, `log::warn!` in the backend. No new error types; `windows-sys` calls wrapped in small `io::Result` functions in `process/windows.rs` and `ipc.rs` only.
- Do not touch `release.yml`, signing, or the macOS nightly's draft policy.

## Non-goals

Everything the spec lists: production Windows release, installer, signing, updater, WSL, ARM64 Windows, Linux, Windows-specific UI beyond title bar and keymap. Also out: making the macOS nightly public, and any refactor of `pty_runtime.rs` beyond extracting the `process` module (file splits are #478 passes 2–4).
