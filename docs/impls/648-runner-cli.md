## Decisions that bind

The spec's decisions 1–8 and its principles. The ones a crew is most likely to get wrong:

- **Inside a mission nothing changes.** `msg post`, `msg read`, `signal` and `ask` append to the event log directly, with no socket, no tokio runtime and no dependency on the app accepting connections. Only the control commands and the outside path use `mcp.sock`.
- **Identity is a handle or the person, never a location (decision 7).** Inside a mission the handle is `RUNNER_HANDLE`. Outside, `--as <handle>` becomes the tool's `from`, validated against the mission's roster by the tool, and no handle means `human`. `mission answer` is the person's verb and takes no `--as`. With a `from` handle the signal tool refuses the person's and the app's own types (`human_said`, `human_response`, `human_question`, `mission_goal`); without one it keeps today's whitelist.
- **A clean rename, no aliases.** `mission_post_human_message` and `mission_post_human_signal` become `mission_post` and `mission_signal`, as the `role_*` cutover did (#604). With decision 8 the CLI is the socket's only client.
- **The order inside 0.11.0 is fixed (decision 8).** Command tree, then the skill on all five runtimes and Jason's smoke of an agent driving a mission with no MCP entry, then the removal. `runner-mcp` keeps working until mission 3, because it is how missions 1 and 2 are launched and watched.
- **One binary.** The control commands live in the same `runner` the mission sessions already have on PATH. No second binary, no scoping by packaging.
- **No new dependencies without a reason in the handoff.** `clap`, `tokio` and `rmcp` are already in `cli/Cargo.toml`; tables are hand-rolled.

## What reading the code changed (2026-09-18)

- **The mission-wide Resume is UI code.** `mission_workspace/actions.rs::resume_open_mission` lists the mission's sessions and calls `ops::session::session_resume` for each stopped one. `mission_resume` is therefore a new backend op with the same loop, not a wrapper. The UI keeps its own loop in mission 1, because its per-session transitions drive the pane state; sharing the op is a follow-up.
- **`ops::session::session_list` already exists and is mission-scoped.** The new `session_list` tool lists direct chats from `repo::session::list_recent_direct`, so its op needs another name.
- **`mission_list` omits archived missions** and `MissionListArgs` has no include-archived flag, so prefix resolution for `mission unarchive` and for `mission show` on an archived mission needs a decision in mission 1.
- **The CLI crate has no lib target and does not depend on the backend,** and the tool registry is `pub(crate)`. The parity test needs a shared list of tool names (a constant in `runner-core` that the backend's registry test and the CLI's command map both assert against) rather than a cross-crate import.
- **`mission answer` takes the `human_question` event id.** `mission_status` already reports it as `pending_asks[].question_id`, which is the id the router matches a `human_response` on.
- **The sidecar is `<app data>/bin/runner`** (`cli_install::install_binary`), and a debug build of the CLI resolves the dev app's socket through `cfg!(debug_assertions)`. Crews never run the dev app, so a crew's live evidence is limited to the not-running path; the wire proof is Jason's smoke against `make run`.
- **Outside a mission with no `--mission`, a mission-scoped command is a usage error (exit 2),** replacing today's soft notice and exit 0. A general CLI that reports success after doing nothing is a trap for scripts. `Partial` env stays exit 2.

## Added to mission 2 (Jason, 2026-09-18)

Proposed after mission 1's smoke and taken into the mission 2 brief when Jason said to start it.

- **Chats get the spawning app's sidecar folder on PATH, as mission slots do.** Today a direct chat passes no `bundled_bin_dir` (`spawn.rs`, "off-bus"), so an agent in a dev-app chat finds Runner through the global skills and can load the production `runner` skill. With the folder on PATH and the skill preferring `runner` on PATH, a session always drives the app that spawned it. The socket stays a compile-time choice (`cfg!(debug_assertions)`); an environment override was considered and rejected because it would let a debug binary reach production.
- **`session show` with the agent status.** No tool returns a direct chat's `AgentStatus` (activity, source, outcome, detail), so a wrong chat status cannot be read from outside the window. A `session show` would have settled a status question on 2026-09-18 in one command.
- **A way to stop or archive a chat.** There is no socket tool for it, so a role with a CLI-started chat cannot be deleted from the CLI.

## Decided on 2026-09-18 after mission 2's smoke

- **The Runner skill is pinned at the top of the Skills pane,** one row per agent, mirroring the MCP pane's pinned Runner row. It replaces the spec's single skill toggle in Settings → General. Open design point for the frame: Codex, Copilot and pi share `~/.agents/skills`, so the pinned row installs or removes the skill for that root, while each agent's own visibility toggle hides it for one agent. **Superseded on 2026-09-19:** one switch in Settings → General, see below.
- **TRAE gets no skill toggle.** Installing the Runner skill into `~/.trae/skills` is enough. TRAE's only switch is `disable-model-invocation` in a skill's own frontmatter, a softer "never pick this by yourself".
- **pi could be toggleable and is not yet decided.** pi's `~/.pi/agent/settings.json` `skills` array supports exclusions, including `-path` to force-exclude an exact path, which the pi spec missed. Unproven: whether an exclusion removes a skill pi discovered on its own in `~/.agents/skills`. If wanted it is Skills pane work for its own issue, not part of 648.
- **The mission 3 gate runs on a nightly, not on `make run`,** because the dev skill fires only on dev wording. The `make run` checklist proves mechanics; the nightly proves the release skill's trigger on a plain request in Claude Code, Codex, pi and TRAE with the Runner MCP entry switched off.

## Decided on 2026-09-19 on the first 0.11 nightly

- **The command stays `runner`,** not `runner-cli`. Checked the registries: Homebrew has no formula or cask of that name and the well-known runners all carry a prefix (`gitlab-runner`, `gitea-runner`, `forgejo-runner`); crates.io `runner` (a Rust snippet runner) had 85 recent downloads, npm `runner` 781 a month and untouched since 2022, PyPI `Runner` is obscure. Product CLIs are named after the product, agents type the name constantly, and a collision degrades safely: a foreign `runner` is never replaced, the skill carries the absolute path, and Runner's own sessions put the app's sidecar first on PATH.
- **The command is installed by default where that needs no prompt,** under the skill's contract: once, recorded in settings, never over something Runner did not create, a removal respected. Jason asked for a setting, then whether it could be the default. macOS targets in order: `~/.local/bin` when it is on the login PATH (where `claude` and `traecli` already live on his machine), else `/usr/local/bin` when it is on the login PATH and writable without escalation. Windows: the sidecar directory on the user PATH. No other folder is a target: the other writable entries on his PATH are nvm's version folder, Homebrew's and Cargo's, which belong to other tools.
- **Where the default cannot act, the explicit Install does what VS Code and Zed do.** Neither detects a PATH: Zed's `install_cli` (read in `~/repos/gui/zed/crates/install_cli`) links a fixed `/usr/local/bin/zed`, trying a plain symlink and then `osascript … with administrator privileges`, and the `code` and `cursor` links on Jason's machine are root-owned in the same folder. `/usr/local/bin` is in `/etc/paths`, so one password puts the command on every Mac's PATH. Runner never edits a shell profile and never prompts at launch. The action lives in the Settings → General row and in the command palette.
- **The Runner skill is one switch in Settings → General, not a row in the Skills pane.** Jason, the same afternoon: a toggle per runtime is wrong, a single toggle is better, and it may not belong in Skills at all. It does not: every other row in that pane hides a skill from one agent, while this installs and removes folders, and the per-agent catalogs would have shown one shared `~/.agents/skills` switch three times. The skill is the agent half of the CLI, so it sits with the command in a Command line section, as Orca does (its General pane has an "Orca CLI" section with a "Shell command" row and an "Agent skills" row; read in `~/repos/gui/orca`). The switch is the truth: on installs for every available, enabled agent and follows the agent switches, off removes all three folders and stays off, and while it is on a folder deleted by hand returns at the next launch. That replaces mission 2's once-per-root record, which respected a hand deletion; `runnerSkillEnabled` defaults on, so a settings file from the nightly keeps the skill. The Skills pane keeps the managed folder as an ordinary row with a "Managed by Runner" badge, so hiding it from one agent still works. This is close to the spec before the pinned-row decision of 2026-09-18, now with reasons.
- **A Windows debug build installs nothing** (my call, open to overrule): a directory on PATH cannot rename `runner.exe` to `runner-dev`, and a debug sidecar directory on PATH would shadow or be shadowed by the release one.
- **Detection alone decides where the skill goes, and the row has no status line.** Jason, reviewing the frame: listing the agents under the switch is redundant, and the skill should be installed for every runtime that is detected. So mission 4 drops the `is_agent_enabled` half of mission 2's eligibility. The Agents switch is about Runner launching an agent; the skill is about an agent in any terminal finding Runner; and the shared `~/.agents/skills` root already leaked past a switched-off Codex whenever pi was on. The description carries the rule ("Installs a skill for every detected agent…"), and a line appears only for a foreign folder or when no agent is detected. Until a build carries this, the nightly still needs TRAE switched on before TRAE's leg of the gate.
- **TRAE's root was skipped on the nightly because TRAE is switched off in Settings → Agents** (`disabledAgents: ["trae"]` in both apps). That is the specified rule, and switching TRAE on installs the skill at once, since `initialize_skill_defaults` reruns when the agent switches change. It also means the default install into `~/.trae/skills` has never run on this machine: the `runner-dev` folder there came from mission 2's stray test write and was only refreshed at startup. The pinned row's install path for TRAE gets its first real proof when Jason switches TRAE on for the gate.
- **Filed and moved:** [#653](https://github.com/yicheng47/runner/issues/653) (a live mission's flag draws in the accent; 0.11), and #630 left the 0.11 milestone for the backlog. `docs/roadmap.md` has not caught up with #630, #651 or #653.
- **Two CLI nits from driving the production app,** for whichever mission touches `output.rs` next: a stopped mission prints `STATUS running` because the mission model has no stopped value, where the curated view could say stopped when no session is live; and `mission stop` prints the crew id where `mission show` prints the crew name.

## Risks

- **The skill is the only way an agent finds Runner once MCP is gone.** MCP tools sit in an agent's tool list; a skill fires only when its description matches what the user said. Mission 2's smoke across four runtimes is the gate for mission 3, and the skill's description is tuned there, not after release.
- **The upgrade step edits three or four user config files.** It goes through the writer Settings → MCP already uses, touches only the `runner` entry of clients in `initialized_mcp_clients`, runs once, and leaves a config it cannot parse alone. A hand-written entry pointing at the deleted bridge will show as a failed server in that agent; the release notes say so.
- **Windows is unproven for the skill path.** The skill carries an absolute sidecar path with spaces and agents there run it under PowerShell or Git Bash; JASONPC proves it in mission 5, which is after the removal lands on `main` but before 0.11.0 is cut.
- **TRAE's skills root comes from its own manual** (`traecli doc skills`, 0.120.52: `~/.trae/skills/<name>/SKILL.md`), not from a live run; mission 2 proves a TRAE session loads the Runner skill.
