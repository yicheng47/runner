**2. Wait timers (`HiZ5G`).** One `format_elapsed(ms: i64) -> String` in `agent_status.rs`: `45s` under a minute, `2m` under an hour, `1h 12m` after, no zero-padding, no seconds once a minute has passed. `StatusPresentation` carries `waiting_since`, the `since` of the oldest interaction (the pane already reports its oldest wait; keep that choice, it is also the one a rollup click opens). `tooltip()` for `Approval`, `Answer` and `NeedsYou` ends with ` · <elapsed>`: `Waiting for you to approve a command or plan · 2m`, `Waiting for your answer · 45s`. The tooltip refreshes every second while it is shown and never otherwise; use whatever gpui gives a tooltip view to schedule its own redraw, and make sure the timer dies with the tooltip. The runner card subtitle appends `· <elapsed>` in the same regular `$text-mid` detail slot as item 1, only once the wait is at least a minute old, minutes-or-hours form only, redrawn on the minute: a rail of cards never flickers with seconds, and no timer runs when no wait is open. Rollups never carry a clock; `StatusRollup::tooltip` is unchanged. No timer on Working, Idle or errors.

**3. Failure attention (`bqwlq`).** `AgentStatus` gains `failed_since: Option<i64>`, the counterpart of `error_since`: the manager sets it (arrival time) when a running session's observation gains `TurnOutcome::Failed`, clears it when the pane is viewed through the same path that acknowledges an error (`mark_viewed` and the manager state behind it; follow the existing call chain from the app's view acknowledgement to the manager and clear it there), and clears it when the outcome leaves `Failed`. Not persisted, no migration. In `agent_status.rs`: `StatusRollup::priority` ranks a set `failed_since` with error, above needs-you; `StatusRollup::tooltip` counts it as its own label, `response failed`, listed right after `error` (so `1 response failed · 1 error · 3 working` is possible and the two are never merged); `StatusRollup::render` draws the red `circle-alert` glyph for it, the same glyph error uses; `target()` opens the oldest unresolved error or failure first, pane order as tie-breaker, as it does for errors today. The single-pane sidebar row shows that glyph in its attention slot while `failed_since` is set, and its tooltip is the pane's: `Response failed · Agent is still connected`. The pane header label, its tooltip and the runner card are unchanged from 347 and keep showing `Response failed` after the sidebar attention has been acknowledged, until the next turn.

**4. Working detail (`z92Zy9`).** `AgentObservation` gains `detail: Option<WorkDetail>` with `WorkDetail::UsingTools` and `WorkDetail::CompactingContext`, serialized snake_case like its neighbours, `None` by default. It is a hook fact: the baseline observation never carries one, and a `Baseline` source with a detail must be impossible by construction, not by convention. Adapters: Claude Code sets `UsingTools` at `PreToolUse` and clears it at the owning `PostToolUse` / `PostToolUseFailure` or the correlated transcript result, using the pending-tool ownership the waits already use (a second tool in flight keeps the detail; the last result clears it); `CompactingContext` from `PreCompact` to `PostCompact`. `claude_settings_args` registers `PreCompact` and `PostCompact` alongside the twelve events it composes today, on both platforms, and the tests that assert that list follow. Codex: the existing `"PreToolUse" | "PreCompact"` and `"PostToolUse" | "PostCompact"` arms split so a tool sets `UsingTools` until its `PostToolUse` and a compaction sets `CompactingContext` until its `PostCompact`. Copilot: `UsingTools` from `PreToolUse` to the owning result or transcript completion, as its waits resolve today; `CompactingContext` from `PreCompact` to the next work event (`UserPromptSubmit`, `PreToolUse`, `PostToolUse`) or `Stop`, because Copilot publishes no `PostCompact`. Compaction outranks a tool in flight while it lasts; when it ends and a tool is still in flight the detail returns to `UsingTools`. Every adapter clears the detail when the activity leaves Working (`Stop`, `Interrupt`, `StopFailure`, bridge loss) and starts a new turn at `UserPromptSubmit` with no detail. A needs-you wait outranks both details in presentation as it does today. UI: `StatusPresentation` carries the detail; `tooltip()` for Working reads `Working · Using tools`, `Working · Compacting context`, or plain `Working`, and the estimated string wins over any detail; the runner card subtitle shows the same detail in the regular `$text-mid` slot from items 1–2 (`Working · Using tools`, `Working · Compacting context`, plain `Working` between details), truncating with an ellipsis rather than growing the card; the header and tab-bar label stays `Working`; rollups never name a detail.
