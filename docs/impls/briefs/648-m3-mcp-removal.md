## Deliverable

Runner registers nothing with any agent, ships no bridge, and cleans up after the versions that did. The socket server, its tool registry and `runner call` are unchanged: the socket is the CLI's transport.

**The upgrade step** (`app_store/mcp_defaults.rs` renamed, `mcp_removal.rs` or similar; `initialize_mcp_defaults` goes). It runs where the defaults run today and acts once: for each client in `initialized_mcp_clients`, read its status; when the `runner` entry is registered and `matches_current` (its command is this app's `<app data>/bin/runner-mcp`, no args) unregister it through the existing write path; when it is registered but points elsewhere (another Runner installation, a hand edit) or the config cannot be parsed, leave it alone and log one line naming the file. Record completion in settings (`mcpRegistrationsRemoved`, default false) only when every client was handled or skipped for one of those reasons; a write error leaves the record unset so the next launch retries, as `initialize_client` does today. `initialized_mcp_clients` stays decodable so a 0.10 settings file loads, and is no longer consulted after the step. A fresh settings file registers nothing anywhere.

**Settings → MCP.** The pinned Runner row, `RUNNER_DESCRIPTION`, the toggles and detail editor path that call `mcp_set_integration`, the config snippet and the environment and endpoint lines go; the caption loses its sentence about Runner's own server. `McpCatalog` loses `runner` and `runner_server`, and `catalog_at` stops seeding a `runner` entry: a `runner` server a user's config still carries (another installation's, or hand-written) is an ordinary row, editable and removable like any other. The catalog of the user's other servers, the runtime dropdown, the detail modal and its editor are otherwise unchanged.

**`ops/mcp.rs`.** `mcp_integration_status`, `McpIntegrationStatus`, `McpConfigSnippet`, `mcp_config_snippet` and the entry builders go with their last caller; `McpClientStatus`, `matches_current`, the per-client status and write functions stay as the upgrade step's tools, and `mcp_set_integration` keeps only the shape the step needs. No dead code left behind; no new public surface beyond what the step calls.

**The sidecar.** `install_mcp_cli` and `MCP_SOURCE_BIN_NAME` go; `MCP_DEST_BIN_NAME` stays for the match and the cleanup. `bootstrap.rs` stops installing the bridge and deletes a stale `<app data>/bin/runner-mcp` (`.exe` on Windows) best-effort: a missing file is fine, and a file held open by a running bridge on Windows is logged and retried next launch. Module and call-site comments describe the result, not the history.
