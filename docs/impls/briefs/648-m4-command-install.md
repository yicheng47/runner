## Deliverable

Settings → General gains a Command line section: `runner` is on the user's PATH after the first launch wherever that needs no prompt and one click away everywhere else, and the Runner skill has one visible switch.

**The command install, backend** (`cli_install.rs` or a sibling module; pure functions over explicit inputs). The name is `runner`, and `runner-dev` for a debug build. On macOS the default target is `~/.local/bin` when that folder is an entry of the login shell's PATH, else `/usr/local/bin` when it is an entry and writable without escalation, else none; no other folder is ever a target. Runner owns a link only when it is a symlink whose target is this app's sidecar path (`agent_skill::sidecar_path`); anything else under the name, in either folder, is foreign, is never replaced, and is reported with its path. Status is one of not installed, installed at a path, foreign at a path, or installed but shadowed by another executable of the same name earlier on the PATH. Install is idempotent. The default never escalates. The explicit Install uses the default target when there is one, and otherwise links `/usr/local/bin/<name>`: a plain symlink first, then `/usr/bin/osascript` with `do shell script "mkdir -p /usr/local/bin && ln -sf … …" with administrator privileges`. The sidecar path contains a space (`Application Support`), so it is quoted for the shell and then escaped for the AppleScript string; get both layers right and test the composed string. A dismissed prompt (osascript error -128, "User canceled") is a normal outcome, not an error. Uninstall removes only an owned link, through the same escalation step when the folder is not writable. The link always targets the sidecar in app data and never anything inside `Runner.app`.

**Windows.** Install adds the sidecar directory to the user PATH: read `HKCU\Environment` `Path` with its type (`REG_SZ` or `REG_EXPAND_SZ`), append the directory when no entry equals it (case-insensitive, ignoring a trailing backslash), write it back with the same type, and broadcast `WM_SETTINGCHANGE` with `"Environment"` through `SendMessageTimeoutW`. Uninstall removes exactly that entry and nothing else. Registry access sits behind a small trait so the tests run against a fake on every platform. `windows-sys` gains the `Win32_System_Registry` and `Win32_UI_WindowsAndMessaging` features, which is not a new dependency. A debug build on Windows installs nothing and its row says so: a directory on PATH cannot rename `runner.exe`, and a debug sidecar directory on PATH would shadow the release one. Shadow detection on Windows looks for another `runner.exe` on the user and system PATH outside Runner's directory.

**The default** (`app_store/command_default.rs`, beside `skill_defaults.rs`). `initialize_command_default` runs wherever `initialize_skill_defaults` runs. It returns early when the store has no home (rename `skill_home` to something neutral if that reads better; tests keep passing `None`). It acts only when `runtime_shell_env` holds a finished discovery with `DiscoveryOutcome::Ok` and a PATH; on anything else it does nothing and records nothing, so the `runtime/changed` refresh tries again. It records `initializedCommandInstall` in settings once it has installed the link, found it already owned, or found a foreign file; it does not record when no target qualifies, so a user who later puts `~/.local/bin` on PATH gets the link once. Any explicit Install or Uninstall also sets the record, so the default never brings back a link the user removed.

**The command row**, first in the Command line section of Settings → General, per the frame: the `runner` command, its state, the installed path, the foreign and shadowed warnings, and one Install or Uninstall button. The escalated path blocks on a password prompt, so it runs off the UI thread, the row shows a busy state meanwhile, and a failure is shown inline in the row.

**Command palette.** Two command items beside "New terminal", shown by state: "Install `runner` command" when it is not installed, "Uninstall `runner` command" when Runner owns it. They run the same action as the row and work from every route, not only while Settings is open (the hole #574's brief had).

**The Runner skill switch**, second in the same section, per the frame: "Runner skill for agents", one switch for all three roots. Its description states the rule, and it has no status line in the normal case or when it is off; a line appears only for an exception, a foreign `runner/` folder (named, never touched) or no supported agent detected yet. It is deliberately not in Settings → Skills (plan, "Decided on 2026-09-19"). The switch is the truth, stored as `runnerSkillEnabled`, default on. `app_store/skill_defaults.rs` changes to follow it: on, the skill is installed in every root that a detected agent reads, at launch and on the `runtime/changed` refresh, and a marked folder deleted by hand is restored. Detection alone decides: drop the `is_agent_enabled` half of mission 2's eligibility, so an agent switched off in Settings → Agents still gets the skill, because that switch is about Runner launching the agent and the skill is about the agent finding Runner. A root no detected agent reads is left alone; off, `agent_skill::remove` clears all three roots and nothing reinstalls. Mission 2's once-per-root record (`initializedSkillRoots`) is no longer consulted; keep the field decodable so a settings file written by the nightly still loads, and default the switch on so that install keeps its skill. A debug build manages `runner-dev`.

**Skills pane.** The managed folder stays an ordinary row in each agent's catalog, so hiding it from one agent still works; it gains a "Managed by Runner" badge through `skill_badges` when the `.runner-managed` marker is present. No other change there.

**`runner status`** gains the command's state and path, in the human view and under a `command` key in `--json`. It is computed in the CLI from the same ownership rule, with the shared constants and pure checks in `runner-core`, as `RUNNER_SKILL_ROOTS` is; the CLI uses its own `PATH` for shadow detection.

**Two small output fixes while in `cli/src/output.rs`.** In the human view, a mission whose status is `running` and none of whose sessions is running prints `stopped` (the mission model has no stopped value; `--json` stays verbatim). And the block `mission stop`, `resume` and `archive` print shows the crew's name as `mission show` does, not its id.

**One debug-only hook.** Jason's Mac has `~/.local/bin` on its PATH, so the escalated path would otherwise ship unproven, with its two layers of quoting. Under `cfg!(debug_assertions)` only, `RUNNER_COMMAND_INSTALL_FORCE_ESCALATED=1` makes the explicit Install skip the default target and take the `/usr/local/bin` path. It is compiled out of release builds and documented in the smoke document and nowhere else.
