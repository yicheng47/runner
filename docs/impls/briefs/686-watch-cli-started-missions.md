## Deliverable

1. **Start means start and watch.** The shipped skill and `runner help agents` both state, as a rule and not only as an example, that after a successful `runner mission start` the agent watches that exact mission through `runner mission feed <id> --follow --json` in the host's own background or watch facility, so later events actually reach it. A follower writing to a log nobody reads does not count. Keep one watcher per mission, bound to its own ID. Say what the agent does when its host cannot deliver background events: tell the user so plainly and give the follow-up command. Name the host facilities only where you have verified them from the installed CLI's own docs or help, for Claude Code, Codex, Copilot and pi; do not start interactive agent sessions or spend model quota to find out. Say in the handoff what you verified and where.
2. **Slower polling.** Replace the fixed 500 ms `FEED_POLL_INTERVAL` with a multi-second default in the 2–5 s range the issue suggests, and say why you chose it. Keep the polling cadence separate from how events are batched into output, and make sure a human question, a stop, a crash or a lost connection still comes through within one poll. Adjust the archive check that currently runs every fourth poll so its wall-clock cadence stays sensible.
3. **Lifecycle.** Today `follow_feed` exits only when the mission is archived. Decide from the code and the issue whether it should also end on a mission stop or completion, and how an expired or broken watch is reported instead of going silent (app gone, mission gone). Routine busy/idle and inbox noise stay hidden by default, as `--all` already controls; failures never do.
4. **Keep the scripting contract.** A plain `runner mission start` still returns its mission ID and JSON and exits; do not make it block. If you add an opt-in start-and-follow form, it must reuse the existing follower and cursor, keep the start result first in the output, and be justified in the handoff; the skill may use it. Whether to add one is your call.
5. **Tests.** CLI tests for the new interval (keep the test-build interval seam), lifecycle exits and any new flag; skill and help tests that pin the watch rule. Existing follower tests (empty and multi-event polls, deduplication, app disconnect) keep passing.
6. **Docs, same diff.** `docs/arch/arch.md` where it documents the follower cadence, the lifecycle and the generated skill; a new `docs/tests/686-watch-cli-started-missions.md` with Jason's smoke: ask an agent with the installed skill only to start a mission, never to watch it, and confirm it arms a watch, surfaces a crew handoff and a human question, and ends the watch when the mission ends.
