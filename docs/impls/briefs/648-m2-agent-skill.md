## Deliverable

An agent with no Runner MCP entry can find Runner, learn the CLI from the binary itself, start a mission and follow it. Spec phases 2 and 3, plus three small additions decided on 2026-09-18.

**`runner mission feed --follow`.** Prints the requested window, then polls `mission_feed` from the last `next_offset`, oldest first, every 500 ms, and prints each new event exactly once as it lands. It exits 0 on Ctrl-C and when the mission is archived (check `mission_get` every few seconds, not on every poll), and exits 3 with the not-running message if the app goes away mid-follow. It reads nothing from disk. `--types a,b` and `--from <handle>` filter client-side in every mode. `session_status` and `inbox_read` are about 95% of a busy log, so the default view and every `--follow` stream drop them unless `--all` or `--types` names them; a plain `mission feed --json` without `--follow` stays the verbatim tool result unless a filter flag is given. With `--follow --json` each event is one NDJSON line, flushed per line so a pipe or a Claude Code Monitor sees it at once, and no `next_offset` line is printed. The human view keeps mission 1's one line per event.

**`runner help agents`.** A compact guide compiled into the binary, so it always matches the installed version: the command tree, `--json` and `-q`, the exit codes (3 means ask the user to open Runner), references by handle, name, id and prefix, and the common flows as copyable commands: find a crew, start a mission with a goal from stdin, follow its feed, answer a pending ask with the question id from `mission show`, post to the lead, stop and archive. It states the identity rule plainly: outside a mission a call with no handle is the person, `--as <handle>` names a roster slot and is refused for a handle not in the roster, and inside a mission the commands carry the caller's own handle. `runner help` and `--help` stay the full reference, and the dead `runner agents --help` pointer from mission 1 goes.

**The embedded skill** (`crates/runner-backend/src/agent_skill.rs`, new). A `SKILL.md` template compiled into the app, with the content the spec fixes: frontmatter `name: runner` and the spec's description; a body that says what Runner is in two lines, names the executable (`runner` when it is on PATH, else the absolute sidecar path rendered at install and quoted, because it contains a space on macOS), points at `runner help agents`, and states the four rules. A debug build renders `name: runner-dev`, says it is the development build, and points at the dev sidecar, so a dev app never overwrites the release skill. Three roots: `~/.claude/skills/<name>/`, `~/.agents/skills/<name>/` (Codex, Copilot and pi read it) and `~/.trae/skills/<name>/`. Each installed folder carries a `.runner-managed` marker. `install`, `remove` and `status` per root, all atomic (temp file, rename). On startup a marked folder whose rendered content differs is rewritten; a folder of that name without the marker belongs to someone else, is never touched, and is reported by `status`. The first-run default (`initialize_skill_defaults` beside `initialize_mcp_defaults`, which this mission leaves alone) installs each root once for the available, enabled agents that read it, recorded per root in settings the way `initialized_mcp_clients` is per client, so a later removal is respected and an agent installed later still gets the skill once. No Settings row in this mission: the toggle is mission 4, design first. `runner status` gains the skill state per root.

**TRAE's skills root.** `RuntimeDefinition::skills_dirs` for TRAE becomes `[".trae/skills"]` (`traecli doc skills`: user-level skills live in `~/.trae/skills/<name>/SKILL.md`; it also reads `~/.coco/skills/` and `~/.trae-cn/skills/`, which Runner does not list).
