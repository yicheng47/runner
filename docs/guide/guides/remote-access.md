# Remote access

Connect this computer to your account so Runner on your other computers can reach its chats and missions. Remote access is a private beta, invite-only and available only in mainland China for now. Signing in to the hosted service needs an account created from an invite code. Sessions are encrypted end to end; the service relays them.

Request an invite code in the [Runner Discord](https://discord.gg/6BrfZdHKNf) or the WeChat user group. **Settings → Remote access** and **Settings → About** provide both links. The WeChat link opens the [README’s Community section](https://github.com/yicheng47/runner#community) for the current group QR code.

Remote access is optional. Signed out, Runner works on this computer alone: nothing on it can be reached from another computer, and the host button's popup lists only this computer and a sign-in row.

Settings lists **Account** and **Remote access** together under **Cloud** because both depend on Runner’s server: Account is your sign-in there, and Remote access connects your computers through its relay.

## Sign in from Runner

1. Open **Settings → Account** and choose **Sign in**, or open **Settings → Remote access** and choose **Sign in to Runner** under **Through Runner’s relay**.
2. Runner shows a short code, a fingerprint and the time left, and opens the approval page in your browser. You can also copy the link or open the short link on another device and enter the code.
3. Sign in, check that the page shows the same fingerprint as Runner, name this computer and approve it.
4. Account shows your account, service, this computer and its fingerprint. If you started from Remote access, that pane shows the relay page once approval completes. If this computer has no PIN, Runner opens **Set PIN** in the Settings window where you started sign-in. Choose and confirm a six-digit PIN so your other computers can pair with it.

When signed in, Account shows its status card and **Sign out on this computer**.

If Runner cannot reach the service, it tries for up to 30 seconds, then returns to Not signed in with an error. Check the service address and your network, then choose **Sign in** again. While sign-in is starting, **Cancel** immediately restores the button. You can retry in the same window or another Runner window; the abandoned attempt does not open a browser or clear the newer enrollment.

## Through Runner’s relay

While signed out, Remote access opens directly on the relay’s sign-in state. Runner’s relay is the only route in this release; Tailscale is planned separately.

The relay page shows the connection, **Allow remote access**, the PIN and paired computers and phones. Its Route section identifies the relay and links to Account. **Reset remote access** makes a new identity, unpairs every computer and phone, clears the PIN and signs out.

While no PIN is set and PIN entry is unlocked, a **Finish setup: set a PIN** row appears below the connection header, with **Set PIN** in place of the Pairing section’s PIN row. Canceling the PIN dialog keeps this row available, including while paused or reconnecting. After saving a PIN, the setup row disappears and the PIN row offers **Change PIN**.

## Connect from a terminal

Run these commands in your own interactive terminal, including over SSH:

```sh
runner remote login
runner remote status
runner remote status --json
runner remote logout
```

`login` displays the approval link, code and fingerprint. Open the link yourself; it does not open a browser on the computer. After browser approval, confirm the account in the terminal. The default answer is No. After connecting, `login` prints a `runner remote pin` next step if this computer has no PIN. Use `runner remote login --server https://runner.example` to choose another service.

Enrollment needs both input and output attached to a terminal, and is refused inside Runner agent sessions. Agents can read status, list or revoke paired devices, or disconnect the computer. They cannot enroll it, set or change its PIN, unlock PIN entry or reset its identity through `runner call`. Closing the CLI during account confirmation refuses the claim.

## Reach another computer from the CLI

Sign both computers in to the same account. On the computer you want to reach, allow remote access and set its PIN. On this computer, run:

```sh
runner remote computers
runner remote computers --json
runner remote pair <computer-id>
runner remote overview <computer-id> --json
runner remote forget <computer-id>
```

`computers` lists the account's computers, including this one, with their IDs, online status, last-seen time and whether this computer has paired with each. Use an ID from that list. `pair` prompts for the other computer's PIN without echoing it; it requires your own interactive terminal and is refused inside an agent session. A failed pairing is one attempt, and is never retried automatically. `overview` shows the other computer's projects, tabs, missions and sessions.

Each pairing keeps a separate private key and pins the other computer's identity. Long Unicode computer names use a shortened pairing label of at most 64 UTF-8 bytes; the full account name stays unchanged. Later connections use that key. **Forget** deletes this computer's key for the other computer and closes the channel; it does not revoke the other computer's access to this one. **Revoke** on the host removes an incoming pairing. If a connection reports that this computer is not recognized, Runner keeps its saved pairing key: a relay can forge that unauthenticated rejection. Verify the host's fingerprint before explicitly choosing **Forget** and pairing again from the CLI, or submitting **Pair again** in the app. An identity mismatch fails without silently pairing again.

Turning off this computer's **Allow remote access** stops incoming access while it can still reach other computers. Signing out keeps paired keys, and **Reset remote access** deletes them. The app’s host button uses the same pairing and terminal connection as these CLI commands.

## Pair and open another computer in the app

Sign both computers in to the same account. On the computer you want to reach, enable **Allow remote access** and set a PIN. On this computer, choose **Pair** beside it in **Settings → Remote access**, or select it in the popup of the host button in the sidebar footer. Enter the other computer’s six-digit PIN. Each submit makes one attempt; Runner never retries a PIN automatically. A wrong PIN clears the field so you can enter it again. If entry is locked or no PIN is set, follow the dialog’s instructions on the other computer first. Check a changed fingerprint in that computer’s Settings before pairing again. If the listed identity changes while the dialog is open, Runner clears the PIN and shows the new fingerprint for you to verify.

If a computer is listed offline, pairing opens **{computer} is offline** without a PIN field. Check that it is awake, signed in, and has **Allow remote access** on, then choose **Try again** to refresh the listing. PIN entry appears when it is online. If the computer goes offline after you enter its PIN, Runner keeps the PIN hidden in the offline dialog; **Try again** submits it once. A timeout, relay failure or other pairing failure also keeps the PIN, with **Try again** to submit it once more. You can edit the PIN after these failures; a wrong PIN clears it. A listing refresh never submits a PIN automatically.

The sidebar footer shows the usage of the computer the window shows, then the host button (a monitor) and the Settings gear. Click the host button, or press Enter, Space or Down while it has focus, to open its popup above the footer. The popup lists this computer first, with a green tile and **This computer** beneath its name, then a divider and the account’s other computers, including offline and unpaired ones. A check marks the computer this window shows. **Remote access settings** at the bottom opens this computer’s Remote access settings. Each remote row shows online or offline status first, including when it was last seen when available; an unpaired computer adds **Not paired**, such as **Online · Not paired**. A green dot on a remote row means a session there needs input or approval, or a mission has a question. The host button’s dot means another paired computer, other than the one this window shows, needs you. Dots carry no count, and unread output alone does not light them. Runner follows online paired computers while signed in, sharing the follow with open windows. Offline, unpaired and locked computers have no attention follow. Click a computer to switch this window; hold Shift while clicking, or use its window button, to open another window. Choose this computer to return to your local tabs and panes. A local mission keeps its layout and selection; its terminals resume and its feed catches up when you return. Each window chooses independently, and every window opens on this computer after restarting Runner. Your local notification settings continue to apply while a remote window is active; clicking a local chat or mission alert returns a window to this computer and opens that item.

Signed out, the host button has no dot and its popup lists only this computer and **Sign in to use other computers**, which opens **Settings → Account**; you can also sign in from **Settings → Remote access**. Runner does not fetch the account directory or expose cached computers and directory errors while signed out. The host button sits in the footer’s tab order beside the gear. Tab and Shift-Tab move through the popup’s controls; moving past either end closes it, Escape closes it, and focus returns to the host button. Clicking outside the popup also closes it, and focus goes to what you clicked.

If the computer list cannot refresh while signed in, the popup shows a warning below its available rows. Check Account and your connection, then reopen the popup to try again.

In **Settings → Remote access**, use **Refresh** beside the Computers heading to reload the list or retry a failed refresh without leaving the page. Existing rows stay visible while loading, the button is disabled until the request finishes, and a successful refresh clears the warning.

A remote window shows only that computer’s projects, tabs, missions and terminals. Unnamed tabs show their first populated pane’s session title; a name you give the tab takes precedence. Empty tabs show the same start surface as local tabs. Titles follow updates from the other computer. Pinned items, projects and recents use the same sidebar structure; projects and sections can be collapsed. Update the host as well as the client for matching mixed tab/mission and pin order. Opening a remote view keeps its scroll and collapse choices separate from your local sidebar. This client remembers each host’s Show active only choice, open Projects and Chats sections, and collapsed projects, Active groups and link groups across windows and app restarts. A new host starts with Show all and both sections open; projects with no unpinned chats or missions, including projects with only pinned items, start collapsed. Each open window keeps its own working copy; a newly opened remote window starts from the latest saved view. Sidebar rows use the same status indicators as local rows: working, unread, approval or answer needed, and errors. When several sessions need attention, the row uses the local priority; stopped rows are dimmed. A pending mission question keeps its answer-needed indicator. The chat launcher uses the host’s agents and roles and shows its active Claude account. Agent rows use their own configuration; role rows use saved role settings. Recent entries are kept separately for each host. The Role and Crew entries show read-only lists from the host. Browse exported role settings and crew rosters, search or page the lists, and use Chat to start a role directly or Start mission to show the launcher page on that crew's goal step. Refresh reloads the host’s catalog. Role and crew changes are unavailable in this Runner’s remote window; Settings and Archived remain available only on this computer. Choose a tab or mission to open its terminals; the first available tab or mission opens the first time a window enters a computer. When you switch the window to this computer or another one and come back, it reopens the tab or mission you left, with the same pane focused in a split tab, and restores that host’s saved sidebar view; if the host closed it meanwhile, the first available one opens instead. Missions use the same workspace, with Feed, member terminal tabs, the sessions rail, answer cards and message composer. Open or close member tabs as on this computer; that arrangement belongs to this window, while the host owns the roster. Shells already attached to a remote tab or mission can also be opened.

Stopped chats show the paused card with Resume and Archive; shell panes close on every exit, without Stop or Restart. Opening a stopped session leaves it stopped. With both computers updated, selecting a stopped chat or mission member also acknowledges its error and unread indicators. An error already acknowledged on the host stays acknowledged in the remote sidebar; restarting is not required to clear that alert.

Role-backed chats keep their `@handle` until you rename the session or tab. Runtime-only chats can use the agent’s conversation title. Update the host for matching labels; older hosts keep their existing labels.

Use the same island headers, splits, pane controls and sidebar menus to start, stop, resume, fork, rename or archive chats; organize tabs and projects with pin, move and reorder; and, when the host supports it, link or unlink missions to agent chats in the same project with **Link to chat**, **Unlink from <chat>**, or by dragging missions into or out of a chat’s group. Persisted changes appear when the host confirms them, and its desktop sees the same changes. Slow actions such as Fork and loading mission history keep the window’s other terminals responsive. Other actions and mission history can finish while Fork is pending; wait for the new chat to open before operating on it. A host that lacks an action hides its controls; its existing terminals remain available.

In the chat launcher’s default page, **Change** opens the other computer’s folder browser and the project menu lists host projects; a split pane starts in its tab’s project and a neighbouring session’s folder. Choose a project or recent folder, or **Browse folders** to visit its home, enter subfolders and go to Parent. **Use folder** selects it; Escape or clicking outside keeps the previous folder. **New project** uses the same folder menu, and a mission starts in the folder the launcher shows. The launcher's Mission row appears only when the host offers missions, and its crew step lists the host's crews. Remote missions require a crew; Empty mission is available on this computer only. The goal step shows each slot and role; model and effort are omitted because the host catalog does not include slot overrides. A failed start stays on the goal step with its goal; the mission opens once the host’s overview includes it.

Chat tabs use shell panes instead of drawers; a host rejects a chat drawer request. Mission drawers remain available.

A mission’s Feed loads recent entries first; **No events yet.** appears once its initial history finishes loading empty, and **Load older messages** retrieves earlier history. When a remote mission has no roles, the sessions rail shows the empty-roster notice while the feed **Add role** card stays on the host. Questions are answered from their cards, and the composer can address the crew or selected handles. A failed answer or post shows its error and keeps your choice or draft; successful replies appear through the host’s feed. Stop, Resume and Archive use the host’s mission lifecycle. Stopping a mission leaves its drawer shells alone. Member stop, resume and restart appear only when supported; adding/removing roles, private session keys and local file actions stay on the host. Reconnecting refreshes the feed and keeps loaded older entries without sending an answer or message again.

Opening a terminal takes control at its pane’s size. Switching to another tab or mission keeps the terminals of the tabs you opened attached, so switching back shows them at once without taking control again or resizing them on the host. Closing a tab, a stopped chat or a dropped connection releases a hidden terminal. When an agent reprints its whole history, such as after a resize, the terminal waits for the output to pause, for at most half a second, and shows it in one step instead of scrolling through each part. Type, paste text, select, copy and resize as in a local terminal. Its colors come from the host’s terminal palette, the one its agents chose their styling from, so a dark host’s terminals stay dark in a light window; font, font size, line height, cursor style, cursor blink and copy on select follow your own **Settings → Terminal**. A host on an older version of Runner uses your terminal palette instead. On Linux, use Ctrl+V for text/PIN paste and Ctrl+C to copy a terminal selection; with no selection Ctrl+C interrupts the terminal. The browser approves sign-in and manages the account; terminal control uses another Runner app. If the host desktop or another client takes control, the terminal remains visible with typing off and **Take control** above it. Leaving the computer releases its terminal attachments and keeps the last size on the host.

A window showing another computer shows that computer’s weekly usage in the footer, beside the host button and the gear. Click the figures to open **Usage on {computer}**, a read-only popover with that computer’s figures and, when it has several Claude accounts, its active account’s name. The popover has no refresh or agent settings button. While connected to a host on a Runner version that cannot send usage, the slot shows **Update for usage** instead; clicking it opens **Usage on {computer}**, which names the version that computer runs and says to update Runner there. Returning to this computer restores its own figures. The last received figures stay visible at reduced opacity while the route is disconnected.

In the host popup, that computer’s checked row leads its connection line with latency bars and the round trip in milliseconds, such as **42 ms · relay · encrypted**: four bars under 100 ms, three under 200 ms, two under 500 ms and one from 500 ms. The round trip goes through the relay to the other computer and back, so it reflects what typing feels like. From 200 ms the bars, text and host button turn amber; they return to their normal colours below 180 ms. Usage stays at full strength while the link is slow. **Connecting**, **Reconnecting** and **Unreachable** use an icon instead of bars; an older host that cannot measure latency shows **Connected · relay · encrypted** with no mark. The host button is green while connected, amber while slow or reconnecting, red when the computer cannot be reached or access is not recognized, and grey once it is forgotten here. The gear switches the window back to this computer and opens its Settings.

A route that receives nothing for about 15 seconds reconnects automatically. Typing during a short write stall is kept in order, up to 1 MiB. During reconnection, typing is dropped; it is never replayed. If queued input is discarded because the route changes or its buffer is full, the remote window shows an error for the affected visible terminal. After a connection to the local daemon is restored, terminal panes load fresh snapshots without taking control again. Terminals of other open tabs do the same when you return to them, as do those hidden when the connection to the computer dropped. If a terminal cannot reattach, it shows an error; select its tab again to retry. If Runner cannot reach the computer, choose **Reconnect** or **Close Tab** to return to this computer. If access is not recognized, the saved pairing key stays in place. Verify the other computer's fingerprint before choosing **Pair again**. Submitting it explicitly forgets that saved key before making one PIN attempt. A failed **Take control** shows an error in the pane; use **Take control** again to retry. Choosing the computer this window already shows keeps its current terminals unless the connection has failed. The popup’s **⋯ → Forget** deletes this computer’s outgoing key and shows that it was forgotten here; pair with its PIN to open it again. **Revoke** removes incoming access. Neither action stops the remote agents.

## Pause, retry or sign out

Turn off **Allow remote access** to close the connection while keeping this computer on the account. The web panel shows it offline. Turn the switch on to reconnect with the same key and fingerprint.

**Sign out on this computer** in Account, or `runner remote logout`, deletes this computer's enrollment credential first and asks the service to remove it once. If the service cannot be reached, Runner reports that the computer is still listed offline; remove that entry in the web panel. Runner asks for confirmation before signing out in the app. Restarting Runner does not reconnect a signed-out computer. Signing in again needs a new code and keeps the same identity key and fingerprint, PIN and paired devices. Signing out returns any window showing another computer to this one.

If the computer was removed in the web panel or the account was deactivated, Runner stops the connection. Account shows the reason even when an old enrollment remains; Remote access returns to relay sign-in. **Try again** uses the existing credential, which can work after an administrator reactivates the account. **Sign in again** clears the old enrollment and starts fresh. Other stop reasons explain whether to retry, approve a new code or update Runner.

Remote access never stops your agents or sessions. Closing the desktop app leaves the connection with the background daemon; stopping the daemon closes it. Release builds keep keys and credentials in the macOS Keychain or Windows Credential Manager. Linux release builds use plaintext mode-0600 files in `${XDG_DATA_HOME:-~/.local/share}/com.wycstudios.runner`; development builds use the separate `com.wycstudios.runner-dev` root. macOS development builds also use mode-0600 files under the development data directory. These store the host identity/PIN, outgoing pairing keys and a credential per service. Keep the data directory owned by your user and not writable by others. The Linux GUI, CLI and systemd user service must use the same `XDG_DATA_HOME` to share the same identity. No desktop keyring is required on Linux; over SSH, start the user service explicitly before enrolling through an ordinary interactive terminal. Existing macOS development Keychain secrets are not copied into files; sign in and pair again when first using that storage.

## Who can reach this computer

The service routes connections to computers on your account. Terminal access requires a paired computer: signing in to the account alone is not enough. Treat paired computers as trusted to operate your chats, missions, projects, roles and crews as well as type into terminals. New chats use the host’s active Claude account. Settings, account selection, and restoring or deleting archived items stay on the host.

Set a PIN from the setup row in **Settings → Remote access → Set PIN**, or run `runner remote pin` in your own interactive terminal outside a Runner agent session. Choose a 6-digit PIN, then enter it again. Any six digits are allowed, including leading zeroes. If you choose repeated single digits, an ascending or descending sequence, or a common PIN, Runner warns that it could be guessed within five tries. **Use this PIN** keeps your choice; **Choose another** clears the entries so you can pick again. The CLI shows the warning in English and Chinese and asks for a separate `y` or `yes`; Enter alone cancels without changing the PIN. The CLI hides both entries; Runner never shows the PIN again. **Change PIN** replaces it without unpairing existing devices. Changing the PIN, turning off **Allow remote access**, signing out or resetting remote access invalidates pairings still in progress, including confirmations waiting for their trust save.

Runner does not send the PIN to its service. Pairing requires the PIN; account credentials alone do not grant terminal access. The PIN exchange prevents offline guessing, while the lock below limits online guesses. Another Runner, or a phone, enters the PIN once to pair and uses its own key on later connections. The section headed **Computers and phones** lists every computer on your account, with this computer first; phones paired with this computer follow the computers. Each row shows whether it is online, offline with its last-seen time, or connected to this computer. The access column distinguishes **↙ Can open this computer**, **↗ This computer can open it**, **⇄ Both ways**, and **Not paired**. Pairing grants access in one direction; both ways requires pairing from each computer. The incoming label matches a paired device’s name to the account’s computer name; it does not grant trust. Paired phones, and paired devices with no matching account computer, with a pairing label shared by multiple account computers, or with multiple keys using the same computer name, remain listed as separate rows below the computers. A phone is recognized by the type its client reports each time it connects, and never matches a computer by name. A device that paired before Runner recorded this, or that has not connected since, shows the computer icon until it connects. Each such row shows the name the device paired with first, and its **⋯** menu shows the fingerprint above its own **Revoke**. An ambiguous label attributes incoming access to neither computer. The row’s **⋯ → Revoke**, or `runner remote revoke <fingerprint>`, removes incoming trust. Use `runner remote devices` or `runner remote devices --json` to read the list from a terminal. The CLI also reports `Connected`, true while that device has an authenticated channel open; JSON uses `connected`. Revoke closes all of that device's channels.

Five failed pairing confirmations in a row lock PIN entry. A wrong PIN and a damaged encrypted confirmation both count; malformed frames do not. Runner shows a warning and **Unlock** in Settings; no new device can pair until you unlock it. Already-paired devices keep working. Changing the PIN does not unlock entry. The lock survives a restart.

Runner shows **{computer} paired** as a system notification when another computer pairs. Clicking it opens **Settings → Remote access**. Linux also shows the in-app toast because it cannot query desktop notification delivery. If system notifications are unavailable or off, an in-app toast says that the computer can now reach this one and offers **Open Remote access**. A reconnection does not raise another pairing notification.

If you suspect this computer’s identity key has leaked, choose **Reset remote access**, or run `runner remote reset-identity` in your own interactive terminal. Confirming disconnects the computer from the account, creates a new key and fingerprint, clears the PIN and all paired devices, and unlocks PIN entry. The pane returns to relay sign-in. Signing in again needs a new code. Your agents and sessions keep running.


## Take a terminal back

Remote control applies to an entire tab, including its split panes (and the drawer in a mission workspace). Taking control of one terminal takes every running terminal in that tab. The host shows one centered **Controlled from {computer}** card with **Take back** over the tab. The remote computer sets the terminal’s size. The covered pane sends neither its own size nor terminal input, including typing, paste, file drops and IME composition. A mission composer submission addressed to a covered terminal keeps its draft until you take the terminal back.

Choose **Take back**, or press Enter on the card, to return the whole tab to this desktop and fit each terminal to its own pane. Each pane keeps its own size. Restarted and newly added panes follow the tab’s current controller; moving a pane to another tab gives it that tab’s controller. A mission shows one card when one computer controls all its terminals.

Closing one remote pane leaves the remaining panes under that computer’s control, and switching its window to another tab or mission keeps control of this one. When it leaves this computer or disconnects, every terminal keeps its last size. The card changes to **{computer} has left** with **Continue here**. Choose it, or press Enter on the card, to fit the terminal here and continue. If Runner did not see the computer’s name, it says **Another computer has left**.

Several desktop windows can show the card, and you can take control back from any of them. With no remote computer using the terminal, desktop input and resizing work as usual. Use the CLI above to pair and read another computer’s overview; opening its terminals in the desktop follows with the host button.
