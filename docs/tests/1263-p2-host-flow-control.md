## Approval fixture limitation and scope decision

Jason authorized one extra private QA chat in message `01M74VQZRFC4BS59CDX95B1KXB`, using explicit launch permission arguments, a fresh scratch cwd and a harmless `/bin/sleep 1` escalation to be denied after both host and remote indicators were captured. However, inspection of its actual Codex process showed neither permission argument pair. Source inspection confirmed that direct chat spawning and resumption strip stored role permission arguments. No supported per-chat permission setter was found. This is a fixture prerequisite failure, not evidence that approval propagation failed.

The same owned chat was stopped before any approval test prompt was submitted, then archived. No second follow-up chat was created, no approval was accepted, and no global runtime or agent permission setting was changed. `approval-role.json`, `approval-fixture-observations.txt`, `approval-launch-permission-source.txt`, the official stop response and `evidence/98-approval-chat-stopped.jpg` preserve the mismatch. QA escalated the missing supported isolated fixture through `runner signal ask_human`. The original runtime-policy rejection in `evidence/37` also remains retained. The check was initially reported Blocked; it was never treated as a successful approval execution.

Jason's answer in Runner message `01M7513694M1GDJEBF5BQFERSY` confirmed the exact prerequisite limitation: direct-chat spawning replaces the role's permission arguments, and no supported per-chat fixture exists without a global change. He directed no further attempts and requested reviewer's scope decision on whether approval is a separate required path for this diff. No additional launch is pending.

Reviewer decided in `01M751A8AHZXQ87C7C7J5B1079` that approval is **not separately required** on exact f4d0a32a. Approval is `Status::NeedsYou` with reason `Approval`, fields of the same `SessionStatus` that carries the passed states; it has no separate message or delivery path. Status change detection and `StatusPush` delivery are unchanged, the overview hash removes every status key regardless of its value, and the client applies the whole status object. Reviewer clarified in `01M751ANFHA9DQZC1E6AC5MJ2E` that `reason` always serializes, as null or a value, so approval is excluded from the hash exactly as the passed states are. Sidebar approval rendering is unchanged. Pacing treats every `StatusPush` as priority traffic. An already-pending state is included in the unsuppressed first overview; adding a new session changes the overview hash regardless of its approval state. The final scope therefore records approval **not run, not required (Skipped)** rather than Passed, while preserving both blocked fixture attempts. All other required checks passed, so `needs-live-test` may be removed under Jason's stated condition.
