## Signal audit — 2026-09-14

Checked against the installed Claude Code 2.1.270 implementation and cmux `015991fbd90cef2ce16b46a58d6f1a265ef81998`. Claude's [hook reference](https://code.claude.com/docs/en/hooks#notification) also documents the delayed notifications and distinct MCP URL subtype. This table records code coverage, not live smoke results.

| Signal | Coverage and limits |
| --- | --- |
| Prompt and tools | UserPromptSubmit and PreToolUse start work. A normal tool result keeps an active turn Working; it cannot erase an ended or interrupted outcome. |
| Question and plan approval | Named AskUserQuestion/ExitPlanMode tool events raise attention immediately. Later notifications keep the same interaction. Runner does not track planning mode or expose plan controls. |
| Ordinary permission prompts | PermissionRequest raises Approval needed immediately when matched to a pending PreToolUse by tool-use ID if supplied, otherwise tool name and structured input. Same-input ambiguity retains all possible owners. Hook results or correlated transcript results clear the owning wait. Automatically handled requests can briefly raise attention until their result. Notifications remain a delayed fallback; sandbox network approvals do not emit PermissionRequest. PermissionDenied is an auto-mode denial signal, not a reliable manual-cancellation signal. |
| MCP forms | Elicitation records possible owners; the delayed notification surfaces a wait. ElicitationResult resolves the matching ID or a unique server candidate. A late notification with no pending form is ignored. Automatically answered requests can leave ambiguous candidates until turn end. |
| MCP browser/URL requests | Unsupported. Accepting the link can leave a second blocking confirmation dialog; the completion notification places request identity only inside prose. Supporting the opening signal alone would not provide reliable cleanup. |
| Completion and API failure | Stop and StopFailure establish internal Ready activity with Completed/Failed outcomes; the UI presents these as Idle/Response failed. Subsequent UserPromptSubmit or PreToolUse clears the outcome and restores Working. idle_prompt is secondary confirmation after an idle delay and preserves the failure label. |
| Escape and Ctrl+C | Input during ordinary active work returns to Idle/Interrupted; Claude can cancel before emitting any turn-end transcript record. Late tool results preserve that state. Open dialogs retain their wait until a matching hook/transcript tool result resolves them; a cancelled dialog's turn_duration confirms Idle. Repeated input after recovery cannot revert Idle to unavailable. |
| Process exit | Runner owns process lifecycle and exit-code attention independently of CLI hooks. |
| Background agents, compaction, and mode switches | Subagent and background-completion notifications do not complete the parent session. Compaction details, dedicated mode tracking, and background-agent attention are not implemented in this slice. |
